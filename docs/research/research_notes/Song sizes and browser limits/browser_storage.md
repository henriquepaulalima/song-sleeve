# Browser support for storing one music file

> **Current decision (2026-10-07):** the user has approved a per-song maximum of 30 minutes AND 128 MiB across all clients/sources. Both limits are inclusive. Proposal-only wording below is the original research snapshot; use the [approved policy](../../../implementation-plan.html#approved-song-limits) for current enforcement. Implementation tests remain pending.

## Can common browsers persist one 5–500 MB music file?

### Takeaway
Current Chrome, Edge, Firefox, and Safari have APIs capable of storing a 128 MiB file, and potentially a 500 MiB file, when this origin has sufficient effective quota and free device storage. This is conditional API support, not a vendor guarantee for a particular device; a quota figure is neither a per-file ceiling nor a RAM budget.

### Inferences
- No current major browser needs to be labeled categorically incapable of storing one 128 MiB file. The negative cases are unsupported old APIs, incompatible implementation paths (for example Safari 18 with an async-only writer), denied/unavailable storage, insufficient quota/free space, and private/embedded restrictions.
- Current OPFS implementations can in principle store 500 MiB too; no cross-browser published per-file guarantee was located. A matrix should say conditional, not guaranteed, and not mark Safari unsupported merely because original-file pickers are absent.
- Prefer OPFS for audio, IndexedDB for catalog. For older Safari use a dedicated-worker sync writer; feature-detect actual root/read/write operations instead of testing only `navigator.storage.getDirectory`. A tested IndexedDB Blob/chunk fallback is possible, but storing a 500 MiB object as a single IndexedDB record should not be assumed robust without device tests.
- If supporting only current Safari 26+ one async writer is simpler; adopting that baseline is a product decision rather than a discovered universal requirement.
- Capacitor's native `Songs` directory should use its native filesystem adapter; WebKit's 15% embedded web-storage figure does not limit files written through that native adapter.

### Gaps
- No hardware tests were performed. API availability is not proof of successful full-file transfer, storage, decoding, or uninterrupted playback on an older phone.
- No reliable official universal per-OPFS-file or per-IndexedDB-record ceiling across all engines was found. Engine versions, device pressure, storage partitions, enterprise policy, and private mode can change outcomes.
- Edge Android does not have a dedicated BCD row; runtime detection and implementation tests are necessary instead of inventing a release number.

## What quotas, persistence, and deletion rules apply?

### Takeaway
Origin quotas are generally much larger than a song; successful writing and retention still depend on available space, storage pressure, and persistence. The aggregate library, staging copies, and other origin data all compete for this budget.

### Cited Findings
- Firefox best-effort quota is `min(10% of total disk, 10 GiB)` with a same-site group limit. Granted persistent storage allows `min(50% of disk, 8 TiB)` without that group limit. Chromium permits roughly 60% of total disk per origin. These are total-disk-derived caps, not free space. — [Mozilla quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- From Safari 17/iOS 17/macOS Sonoma, WebKit browser origins have up to 60% total disk, embedded nonbrowser apps up to 15%; overall caps are 80%/20%. Standalone home-screen/dock web apps receive browser quotas. Cross-origin frames get 10% of their parent origin's quota. — [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- WebKit says estimated quota is not guaranteed writable capacity; persistent mode is heuristic, with installed home-screen web apps an example signal. Best-effort origins may be removed under disk pressure, overall-cap excess, or inactivity. — [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- `estimate()` reports approximate origin usage/quota; writes past the actual quota fail with `QuotaExceededError`. Persistence reduces automatic eviction but is not a replacement for cloud backup; users can clear site data. — [Mozilla quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Google OPFS guide](https://web.dev/articles/origin-private-file-system)
- Private sessions may use different quotas and normally delete data when they end. `localStorage`/`sessionStorage` are only 5 MiB each per origin and are string-oriented: unsuitable for audio payloads. — [Mozilla quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- Current Chromium source sets an incognito storage pool to a randomized 15–20% of physical RAM and each storage-key quota to one-third of that pool (approximately 5–6.67% RAM). This is an implementation detail, not a stable API contract; it illustrates why normal-mode disk percentages cannot predict private-mode capacity. — [Chromium quota settings source](https://chromium.googlesource.com/chromium/src/+/main/storage/browser/quota/quota_settings.cc)

### Inferences
- At 4 GiB RAM the current Chromium incognito formula yields about 205–273 MiB per storage key before other consumption; a single 500 MiB file cannot fit that quota even though normal disk-based quotas may permit it. A 128 MiB file may fit but cannot be promised. Treat these as formula illustrations, not guarantees for deployed versions.
- For one file of size S, preflight `quota - usage` against required new data plus staging/write overhead and a reserve. For example, a conservative app heuristic is `2 × S + 32 MiB` additional headroom when write behavior can require a temporary copy, while already-used old content remains in `usage`. That heuristic is not a browser requirement or guarantee.
- Browser capacity tests should include normal/private sessions, denied persistence, low disk, origin eviction, and changing deployment origins. Vercel preview domains create distinct origin stores; the production origin must remain stable.
- Optional web offline storage must report `Not downloaded` if data was evicted; never delete account track metadata just because OPFS bytes disappeared. Re-download synced tracks; unsynced files need re-selection when their browser source is unavailable.
- Old Safari fixed 1 GiB initial quotas should not be represented as the modern universal Safari limit.

### Gaps
- Persistence is granted by browser heuristics or a Firefox prompt, so there is no universal guarantee that a specific user/library will receive it. Private-mode storage availability is version dependent: use a small write/read/delete probe and handle failure.
- No precise universal browser-level storage overhead ratio exists; the reserve formula must be validated for chosen write strategy and tested devices.

## Does browser storage support prove whole-file playback is safe?

### Takeaway
No. File storage quota, transient Blob storage, JavaScript heap/ArrayBuffer allocations, media decoding, and OS tab termination are separate constraints. A proposed 128 MiB / 30-minute web envelope can cover long compressed music but remains a product/test target, not a supported-memory promise.

### Cited Findings
- Chromium's Blob design says renderer-held Blob objects refer to data in the browser process; large Blobs may spill to disk. Creating large Blobs too quickly can cause renderer out-of-memory, and retained Blob/object-URL references prevent cleanup. The source documents implementation-level memory/disk budgets, not universal per-file capacities. — [Chromium Blob design](https://chromium.googlesource.com/chromium/src/+/main/storage/browser/blob/README.md)
- OPFS `getFile()` produces a File/Blob usable with `URL.createObjectURL()`. OPFS supports incremental writes; worker synchronous access avoids blocking the UI. — [Google OPFS guide](https://web.dev/articles/origin-private-file-system)
- `decodeAudioData()` consumes complete file data and produces an AudioBuffer containing decoded audio. This differs from using an HTML audio element. — [MDN decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData), [MDN AudioBuffer](https://developer.mozilla.org/en-US/docs/Web/API/AudioBuffer)

### Inferences
- Preserve the user's entire-selected-file-before-play rule with one owned File/Blob and one object URL. Do not assume that Blob means the bytes are all resident in JavaScript RAM or that loading a complete file requires creating a complete ArrayBuffer.
- Avoid base64/data URLs, whole-file ArrayBuffer duplication, or decoding entire long tracks through Web Audio merely to play them. Decode metadata incrementally/in a worker where practical and play through HTMLMediaElement.
- A 30-minute, stereo, 44.1 kHz decoded Float32 AudioBuffer would contain `1800 × 44100 × 2 × 4 = 635,040,000 bytes`, about 606 MiB, before overhead. This is a calculation illustrating that a ~72 MB compressed file can have vastly larger full decoded representation; ordinary HTML audio playback need not allocate the full decoded track this way.
- One active 128 MiB Blob may work well across tested browsers; 256/500 MiB stress files should characterize failures rather than automatically become MVP accepted limits. Release/cancel old playback resources before acquiring the next selected file; a currently pinned file prevents fetching another version simultaneously in the existing design.
- If selecting 30 minutes and 128 MiB, enforce BOTH separately: a 3-minute high-resolution PCM file can violate size; a small low-bitrate hour-long file can violate duration. Do not describe every file under the storage quota as a playable supported format.
- Downloading incrementally into a staging OPFS file but beginning playback only after complete download/validation remains download-before-play; it does not introduce cloud streaming playback. Making OPFS mandatory for transient web playback would, however, be a new product architecture choice and should be marked proposed, not silently imposed.

### Gaps
- No official source promises that a 128 MiB whole-file Blob is safe in every major browser/device. Practical limit needs tests on low-memory Android/iPhone, desktop Safari/Firefox/Chromium, tab backgrounding, and repeated track switches.
- Native file adapters and codec/container support are different investigations; this notes file does not claim that every storable audio format is decodable everywhere.
