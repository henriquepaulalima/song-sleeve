# Catalog, API, and sync architecture review

Research checked 2026-10-06. PostgreSQL links point to the current official documentation (PostgreSQL 18 as of this review); Gin links are official documentation; RFC 9700 was published January 2025.

## Are the PostgreSQL entities and relationships minimal, coherent, and safe under multi-user/concurrent use?

### Takeaway
The core catalog model is directionally sound, but the current table list mixes four different concepts—logical library entries, imported source provenance, physical audio versions, and per-device playable locations—and leaves most ownership, cardinality, and deletion rules implicit. Clarify those concepts and enforce tenant boundaries and membership semantics in PostgreSQL before implementation; otherwise valid UI actions can create cross-user references, duplicate tracks/assets, dangling sync state, and irreconcilable order.

### Cited Findings
- The plan describes `track_sources` as provenance per track, a per-device `device_song_locations` map, a stable `tracks` identity, one optional `media_assets` per track, and separately a `track_assets` relationship for one or more encodings/versions. It also says one user can add a song from local storage or Drive, and multiple devices can have distinct local locations. Those definitions do not establish whether a source belongs to a logical track, a particular imported file/version, or a device location. (Plan: [Data model](../../../implementation-plan.md#data-model); [Import from a source](../../../implementation-plan.md#import-from-a-source).)
- PostgreSQL foreign keys can reference one or more columns and require a matching unique/primary key on the referenced columns; using composite `(user_id, id)` keys therefore lets the database enforce same-user ownership for tracks, artists, playlists, groups, assets, and memberships, rather than relying solely on handler checks. [PostgreSQL `CREATE TABLE` / foreign keys](https://www.postgresql.org/docs/current/sql-createtable.html)
- PostgreSQL unique constraints enforce uniqueness across a column set; unique indexes can also be partial when uniqueness should apply only to a subset of rows. This supports constraints such as `(user_id, normalized_name)` for artists and `(user_id, playlist_id, track_id)` for playlist membership, plus partial uniqueness for nullable/polymorphic cases where appropriate. [PostgreSQL constraints](https://www.postgresql.org/docs/18/ddl-constraints.html), [PostgreSQL `CREATE INDEX`](https://www.postgresql.org/docs/current/sql-createindex.html)
- The plan says artist edits/imports will enforce a same-user composite reference, but does not specify equivalent composite references for playlist items, group-playlist memberships, source records, asset rows, sync scopes, or job rows. This inconsistency leaves the strongest tenant-integrity measure applied only to artists. (Plan: [Authentication and library API flows](../../../implementation-plan.md#authentication-and-library-api-flows-for-these-screens); [Data model](../../../implementation-plan.md#data-model).)
- The Markdown and HTML models are not in parity: Markdown includes `cloud_sync_scopes` and says `cloud_sync_jobs` stores a membership snapshot/per-track progress, while the HTML data table instead shows `cloud_sync_settings` and omits `cloud_sync_scopes` and the snapshot detail. This leaves uncertainty about the canonical model and is a concrete doc-review defect. (Plan: [Markdown data model](../../../implementation-plan.md#data-model); [HTML data model](../../../implementation-plan.html#data).)
- **Current organization decision:** `playlists` are user-created manual collections of songs through `playlist_items`; groups are user-created containers of playlists through `group_playlists`. Artists are optional explicit assignments. Users edit membership/order; groups never contain groups or direct tracks. (Plan: [Organize music](../../../implementation-plan.md#organize-music); [Data model](../../../implementation-plan.md#data-model).)
- The plan requires independent order for the library, playlist songs, and group playlists and requires other devices to observe successful changes, but does not define a concurrent-write policy, an order revision, or tie-breaking. PostgreSQL documents that a query without `ORDER BY` has no guaranteed result order, and transaction isolation can require whole-transaction retries under concurrent updates. [PostgreSQL `SELECT`](https://www.postgresql.org/docs/current/sql-select.html), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

### Inferences
- **High — Define logical track vs file asset and remove ambiguous overlap.** For MVP, choose whether a track has exactly one playable audio payload. If yes, fold `track_assets` into `tracks` or a single `track_file`/`media_asset` relation with one current content version. Keep `track_sources` only for genuinely portable provenance such as Drive file IDs; keep all local paths/handles in `device_song_locations`. If users may attach multiple encodings or duplicate source copies to one logical song, retain an explicit `track_files`/`track_assets` child table and define which file is current/preferred. Avoid both “one asset per track” and “one or more assets per track” in the same MVP schema.
- **High — Decide duplicate semantics explicitly.** The UX says import creates songs in one library and computes hashes, but it does not specify if the same bytes selected twice create one logical track, if separate encodings with the same title/artist merge, or whether a second device import attaches a new source to an existing track. Recommend exact checksum as a duplicate suggestion or idempotency aid, not silent merge; keep the user-visible track ID stable and support an explicit merge action only later. Unique per-user checksum constraints should be added only if this chosen behavior truly forbids duplicate library entries.
- **High — Make tenant ownership a schema invariant.** Add `user_id` to tenant-owned rows and composite unique/foreign-key constraints such as `(user_id, id)` and `(user_id, playlist_id) -> playlists(user_id,id)`. For each join table, include user_id and composite FKs to both parents. Keep ownership checks in Gin too, but let the DB reject cross-tenant references and cascade/restrict only according to product semantics. This directly aligns with the plan’s own same-user artist FK rule.
- **High — Separate import provenance from location.** A logical track may have different original source identities on different devices, and link-vs-copy is explicitly device-specific. Model `device_song_locations` as authoritative for playable references and local mode. Treat `track_sources` as optional external provenance attached to a particular imported file/content record, or drop it from the first schema if there is no cross-device product behavior requiring it. Do not imply one singular required “origin” per track when library sync can create a catalog record without any bytes on the receiving device.
- **Medium — Simplify scope identity.** `cloud_sync_scopes(user,type,collection)` is polymorphic: a nullable collection ID cannot have a normal FK to either group or playlist, and a library scope has no collection row. Prefer an explicit `scope_type` plus nullable target with check constraints and separate partial unique indexes for library/group/playlist scopes, or use distinct scope tables if those types later acquire distinct lifecycle rules. Add real FKs for group/playlist target rows where possible. PostgreSQL partial unique indexes are appropriate for uniqueness applying only to rows with a given type. [PostgreSQL `CREATE INDEX`](https://www.postgresql.org/docs/current/sql-createindex.html)
- **Resolved — Keep organization minimal.** Keep only artists, manual playlists, groups of playlists and their explicit relationships. Retain `library_view_preferences` for the Songs/Playlists/Groups visibility checkboxes. Reject unsupported child types and parent/rule payloads rather than adding recursive collection models or inferred memberships.
- **Medium — Specify order write contract.** Keep one integer position per ordered scope and perform full reorder in one transaction for MVP. Require stable IDs and a monotonically increasing `order_revision` (or playlist/group version) in the request, reject stale updates with a conflict response, and have clients refetch/reapply. Query every ordered list with deterministic `ORDER BY position, id`. This is simpler and more understandable than introducing fractional ranking until reordering volume proves it necessary.
- **Medium — Define lifecycle/delete constraints.** State FK delete behavior: deleting playlist removes membership/config only; deleting group removes group associations only; deleting track removes playlist memberships, local maps, cloud asset reference and eventual object deletion job; removing artist assignment sets `artist_id` null; account deletion cascades account rows while cloud bytes are asynchronously purged. Avoid trying to perform PostgreSQL and object-store deletion as one atomic transaction; use an explicit deletion state plus retryable cleanup job.

### Gaps
- The plan does not state if one track may have multiple audio encodings, whether the same exact file may intentionally appear twice in a user's catalog, or whether source provenance must be globally portable across devices.
- There is no schema diagram or concrete migration/index list, so cardinalities, nullable uniqueness, cascade policies, and actual columns cannot be audited fully.
- Organization scope is resolved: groups contain playlists, playlists contain songs, and users explicitly create and change their membership.

## Do the Gin API boundaries and account/catalog operations have a simple, robust ownership model?

### Takeaway
A single modular Gin API is a good fit for the stated scale and keeps product boundaries understandable. The plan should describe Gin as the HTTP adapter, keep business rules in a small set of transactional application modules, and add a durable outbox/idempotency contract for email, offline catalog writes, and async media work; without that, handlers and separately described services will duplicate rules and lose work between PostgreSQL and external systems.

### Cited Findings
- The plan proposes a modular Go application with Gin routes calling account, catalog/artists/organization, import, storage, and synchronization services, plus separately deployed worker service(s). It does not define exact ownership boundaries or whether those services are packages, processes, or independently deployed services. (Plan: [Repository and service shape](../../../implementation-plan.md#repository-and-service-shape); [Recommended stack](../../../implementation-plan.md#recommended-stack).)
- Gin's documented feature set includes HTTP routing, middleware, request binding, and validation; its middleware model lets cross-cutting authentication/authorization be attached to route groups, while request binding can return a client error before application logic runs. [Gin middleware](https://gin-gonic.com/en/docs/middleware/using-middleware/), [Gin binding and validation](https://gin-gonic.com/en/docs/binding/binding-and-validation/)
- Gin explicitly warns that goroutines started from middleware/handlers must not retain the original request context; async work needs its own context/lifecycle. That supports persisting jobs and letting a worker own background execution rather than launching detached request goroutines. [Gin goroutines in middleware](https://gin-gonic.com/en/docs/middleware/goroutines-inside-middleware/)
- PostgreSQL documents `FOR UPDATE SKIP LOCKED` as unsuitable for general-purpose reads but useful for multiple consumers of a queue-like table, which supports a simple Postgres-backed job/outbox queue before adding Redis or a separate broker. [PostgreSQL `SELECT` locking clause](https://www.postgresql.org/docs/current/sql-select.html)
- The plan requests one-time email verification tokens, session revocation, rotating refresh credentials, local offline writes, cloud jobs, and eventual change-log sync. It does not model an email outbox, notification-delivery record, client mutation ID/idempotency key, or per-device change cursor. (Plan: [Authentication and library API flows](../../../implementation-plan.md#authentication-and-library-api-flows-for-these-screens); [Data model](../../../implementation-plan.md#data-model).)
- RFC 9700 states refresh tokens for public clients must be sender-constrained or use refresh-token rotation and describes retaining token relationships to detect replay. [RFC 9700, §4.14](https://www.rfc-editor.org/rfc/rfc9700.html)

### Inferences
- **High — Keep one deployable modular monolith.** Use Gin routes/DTOs, middleware for authentication/rate limits/request IDs, and application modules: `account`, `catalog` (including artists, playlists, groups, ordering, preferences), and `media` (sync scopes/assets/jobs). These are code ownership boundaries, not network services. The storage adapter is an infrastructure package. Run one API process and one worker process from the same Go module/image only when work exists; avoid splitting artist, playlist, group, and catalog services because their updates need common transactions.
- **High — Add transactional outbox records.** On registration, create the user/token plus a pending email-delivery outbox row in one PostgreSQL transaction; a worker sends the mail and retries. On catalog changes, persist the mutation and change-log event in the same transaction. On scope confirmation, persist scope state, job, and job-item snapshot atomically. This closes the failure window where the DB commits but email/job/change notification is never enqueued. The outbox pattern is an architectural inference; the specific Gin/PostgreSQL docs above support using durable DB-backed work, but the plan needs to define retry and delivery guarantees.
- **High — Make API operations idempotent for offline clients.** Give each client-generated mutation a stable `operation_id`/idempotency key and device ID; keep a unique `(user_id, device_id, operation_id)` receipt with outcome. Offline retries then do not duplicate imports, artist creation, playlist membership, or cloud jobs. Define conflict behavior for changes to the same field (last-write-wins with server revision may suffice initially) and expose a cursor/change feed. The plan has an offline queue and a change log but currently does not connect them with IDs or conflict rules.
- **High — Keep local file operations client-owned.** The API must not accept local paths or promise it can resync a file: the user picks/relinks through platform UI and the client updates local SQLite. The plan correctly assigns file picking/path updates to clients; add API contracts only for resulting metadata, content version/hash and import state. Do not route file bytes through Gin when direct client-to-bucket upload is available.
- **Medium — Define transaction-aware boundary for “create/reuse artist + import track.”** The API should resolve an existing normalized artist or insert safely under a unique constraint and upsert/idempotently create the track in one transaction. Handle concurrent artist-creation conflicts by reselecting the winner. Keep artist browse/search endpoints in Catalog; a separate Artist service/module adds no isolation benefit for a one-owner artist relation.
- **Medium — Pick a browser/native refresh-token strategy instead of one generic credential phrase.** Browser refresh credentials should be protected using an appropriate secure cookie strategy; Capacitor needs platform secure storage. For public clients, ensure rotation has reuse detection and family/session revocation, not merely overwrite-the-hash. RFC 9700 makes rotation/sender constraint normative for OAuth public-client refresh tokens; whether this custom login flow is formally OAuth is a product/security choice, so document this as a conservative model rather than claiming direct protocol conformance.
- **Medium — Make request/response contracts explicit.** Gin binding/validation handles shape and basic validation, not permission or cross-field business policy. Put ownership checks into every query and use typed request DTOs with explicit error codes for verification-required, stale ordering revision, deleted asset, unverified local source, and duplicate idempotency key. Keep route/controller methods thin and unit-test application services.
- **Low — Authentication model requires security decisions.** Email/password with verification has no password-reset/change, email-change, or account-deletion flow in the plan. These may be later scope, but not modeling how users regain or remove access can create production blockers. Decide before launch whether to implement them in initial auth scope.

### Gaps
- The plan does not specify cookie versus bearer-token transport, access-token format/expiry, browser refresh-token storage, native secure storage, CSRF protections, refresh-token family/reuse behavior, or how “current session” is identified.
- No email provider, mail retry/dead-letter policy, verification token invalidation on resend, or account deletion flow is specified.
- The change-log schema/cursor contract and conflict policy for offline edits are not defined; no authoritative merge behavior can be validated from the current plan.

## Can cloud sync, ordered memberships, and local/cloud copies converge safely across devices?

### Takeaway
The plan contains the right high-level idea—explicit scope opt-in, per-track deduplication, snapshot jobs, client-direct uploads, local downloads, and retryable work—but “synced” is underspecified under scope edits, content replacement, overlapping scopes, and deletion. Treat media as a versioned state machine with durable per-job items, content hashes, idempotent object keys, and reconciliation; distinguish “this scope is enabled” from “all its current tracks have a verified cloud version.”

### Cited Findings
- Current behavior describes cloud scopes for the full library, a group’s union of playlist tracks, or a playlist; sync confirmation snapshots members, reuses one asset per track, reports per-track status, automatically queues future members, and preserves assets when a scope is disabled. (Plan: [Optional cloud sync and local playback](../../../implementation-plan.md#optional-cloud-sync-and-local-playback); [Authentication and library API flows](../../../implementation-plan.md#authentication-and-library-api-flows-for-these-screens).)
- The plan also describes `media_assets` as one optional cloud-backed audio asset per track, `track_assets` as possible multiple encodings/versions, and a media version/checksum. These are competing cardinality statements; a changed local file may need a new immutable object version rather than mutation of the existing object key. (Plan: [Data model](../../../implementation-plan.md#data-model); [Railway bucket upload/download/cleanup](../../../implementation-plan.md#use-the-bucket-for-optional-cloud-upload-download-and-cleanup).)
- The plan says Jobs record a membership snapshot, but the data model lists only `cloud_sync_jobs` with “membership snapshot, per-track progress,” not a child `cloud_sync_job_items` entity. It is unclear whether snapshots are JSON payloads, durable relational items, or regenerated by querying memberships. (Plan: [Data model](../../../implementation-plan.md#data-model).)
- The plan says a group/playlist scope auto-enqueues future songs; playlist/group membership can change, tracks can be deleted, and a song can be in overlapping scopes. These produce state transitions beyond a one-time snapshot. PostgreSQL row locks and serializable transactions provide concurrency tools, but serializable transactions can abort and require retry; the application must define its retry and idempotency behavior. [PostgreSQL `SELECT` locking](https://www.postgresql.org/docs/current/sql-select.html), [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)
- PostgreSQL's `SKIP LOCKED` is specifically documented as useful for queue-like tables accessed by multiple consumers, supporting bounded worker claim loops for outbox/job records without adding a broker at MVP scale. [PostgreSQL `SELECT`](https://www.postgresql.org/docs/current/sql-select.html)

### Inferences
- **Critical — Make each audio content version immutable and addressable.** Do not overwrite the cloud object for a track in place. Model a logical `track` plus a current `content_version` (or a separate file/asset row) with checksum, byte size, media type, local source state and optional cloud object state. A resync that changes bytes creates a new version and only then changes the track's current-version pointer; previous asset cleanup happens asynchronously once no jobs/downloads reference it. This prevents stale device manifests and in-progress uploads from racing a replacement.
- **High — Materialize job items.** Add `cloud_sync_job_items(job_id, track_id, content_version_id, state, attempt_count, error_code, object_key, expected_checksum, updated_at)` with unique `(job_id, track_id, content_version_id)`. Keep snapshot membership explicit and durable instead of an opaque unbounded JSON field or a live query. New membership events create new job items for enabled scopes. The queue can be claimed via transaction and `FOR UPDATE SKIP LOCKED`, with leases/timeouts for workers that crash.
- **High — Define sync status as derived state.** “Synced” should mean every track in the *current resolved membership* has a ready object for the current content version. `Syncing` is any pending/leased/uploading item; `Needs attention` is a current member lacking bytes or with terminal/retryable failure; removed members do not invalidate the cloud asset. The scope row records only whether auto-sync remains enabled. Use a version/revision on scope membership so status reads can know which member set was assessed.
- **High — Use explicit state machine and idempotency for object upload.** Suggested states: `pending -> granted -> uploaded_unverified -> ready`, with retryable/terminal failure and deleting states. Generate an opaque object key per asset version; keep an `upload_attempt_id`, grant expiry, expected size/checksum, and completion idempotency key. A client completion callback is a claim only; server/worker should verify object existence, size, and checksum to the strength promised by product. Never equate a provider's opaque multipart ETag with the content hash unless the provider explicitly defines that checksum.
- **High — Define scope/membership race behavior.** Scope confirmation should in one DB transaction insert/update the enabled scope, read memberships consistently, store job items, and append an outbox/change event. Playlist/group membership changes should transactionally create sync work for all active scopes that now include the track. If confirmation and membership edit race, a serialized retry or a revision check must make the track either included in the confirmation snapshot or queued as a later addition—never lost. Group scope should deduplicate tracks while retaining the source playlist IDs only if the UI needs to explain why they are in scope.
- **High — Separate local availability from cloud availability.** A missing local linked file should not make an already verified cloud version unavailable; the plan correctly says this. Represent these as independent state dimensions, not one `health` enum that could conflate `origin_unavailable`, `cloud_ready`, and `local_copy_present`. Per-device maps stay private/device-local; server metadata only needs content version, source provenance, and cloud state.
- **Medium — Define content matching.** Hash during import to support integrity and exact duplicate suggestions. If an existing track has identical checksum, ask whether to reuse the existing library entry or create a separate track; if the user chooses reuse, attach the new device location to the existing track. If checksums differ, treat as new content/version even if title/artist match. Do not merge based on filename or normalized metadata.
- **Medium — Model clean deletion as a tombstone workflow.** On track delete, immediately tombstone the catalog row and revoke grants; remove relational memberships transactionally; enqueue cloud-object deletion; clear device-local copies on each device when they next receive the tombstone. The current statement that delete removes all device source/location records cannot be synchronously true for offline devices. Clarify that server records are tombstoned centrally and clients erase local data upon next sync; linked original files are never deleted.
- **Medium — Make the app's “sync all” bounded.** Library-wide confirm can represent many songs; paginate/stream item discovery into durable job items and cap simultaneous uploads per device. Show count/estimated bytes and permit pause/cancel. This avoids a request containing every track and keeps the API from holding an entire user's catalog/job in memory. The plan already asks for pagination and workers, but not the job-size/backpressure contract.
- **Medium — Avoid premature service/queue complexity.** PostgreSQL plus one worker and idempotent DB jobs is sufficient for an MVP; do not add Redis, Kafka, or separate media microservices unless job throughput or isolation needs are measured. Separate API and worker deployment from the same codebase is enough to scale cloud I/O independently.

### Gaps
- “Cloud sync” is partly upload to a backup/library bucket and partly cross-device transfer, but the plan does not define deletion propagation, offline tombstones, content-version replacement, cancellation, pause, or what happens when a group/playlist is disabled after job snapshot creation.
- “Synced” is specified as every current member verified, but there is no membership revision or rule for content changing after the check while an upload is underway.
- The current `media_assets`/`track_assets` descriptions do not settle whether there is one content file per logical song, multiple encodings, or full file-version history.
- The HTTP contract omits grant refresh, upload completion verification details, download manifest/version ETag behavior, malware/content validation policy, quota semantics, and whether device-local “Download for offline” records a device intent on the server.
