# Storage, import, and cloud-sync architecture review

Research checked 2026-10-06. Scope: local file/folder import and persistence, Google Drive origin, Railway S3 bucket upload/download, scoped sync jobs, deletion/recovery, and storage-model simplification. Source links below are primary documentation from Capacitor, Android, Apple, Railway, and AWS.

## Can local origins and device file references be made durable across platforms?

### Takeaway

The local-first direction is sound, but a saved URI/path is not a portable or universally durable file reference. Keep origin access strictly device-local and implement native platform adapters (including persisted Android URI grants and iOS security-scoped access) behind a small file-source interface. Make copy-to-app-storage the reliable default for playback across restarts; treat link mode as a best-effort capability with relink UX and platform-specific limits. The current plan's local import, folder scan, reconciliation, and cloud upload all require a native file adapter beyond generic Capacitor Filesystem APIs.

### Cited Findings
- Android's Storage Access Framework returns `content://` URIs; to preserve access across reboots, apps must explicitly take persistable URI permissions. A selected tree URI grants access to descendants, but some locations are excluded on Android 11 and later. [Android: Intent.ACTION_OPEN_DOCUMENT and ACTION_OPEN_DOCUMENT_TREE](https://developer.android.com/reference/android/content/Intent#ACTION_OPEN_DOCUMENT), [Android: shared documents and files](https://developer.android.com/training/data-storage/shared/documents-files)
- Apple's document-picker guidance says external document access uses security-scoped URLs, access must be started/stopped, and apps should not persist bare URLs from open/move operations; use a document picker, metadata query, or security-scoped bookmark. The same guidance notes providers may return a temporary sandbox copy for import. [Apple: Accessing Documents](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/DocumentPickerProgrammingGuide/AccessingDocuments/AccessingDocuments.html), [Apple: Security-scoped bookmarks and URLs](https://developer.apple.com/documentation/professional-video-applications/enabling-security-scoped-bookmark-and-url-access)
- Capacitor Filesystem exposes platform directory abstractions, but its `Cache` is explicitly purgeable. `Data` and `LibraryNoCloud` are documented directories, while filesystem APIs do not themselves describe SAF persistable grants or security-scoped bookmark lifecycle. [Capacitor Filesystem API](https://capacitorjs.com/docs/apis/filesystem)
- Capacitor File Transfer downloads to a file path and can upload a file path, with progress events; its docs demonstrate native uploads from a filesystem URI. This is a transfer API, not a document-picker/provider permission API. [Capacitor File Transfer API](https://capacitorjs.com/docs/apis/file-transfer)

### Inferences
- **High — local link persistence assumption is under-specified.** The plan says device SQLite stores an origin URI/path and access grant, then checks it at each launch. A generic URI string is insufficient: persist Android grant flags and call the platform permission API; store iOS security-scoped bookmark data and scope lifecycle handling. Add an explicit `FileAccessAdapter` contract and spike both implementations before promising link mode on mobile.
- **High — Capacitor alone does not supply the full import capability.** The plan should list a native file-picker/folder-enumeration bridge (custom Capacitor plugin or maintained plugin), because `Filesystem`/`File Transfer` do not cover SAF/document-provider traversal and security-scoped URL/bookmark access. Include providers that return cloud-backed document URIs: reading may block, fail offline, or trigger provider downloads.
- **Medium — folder import is not one uniform behavior.** The requirement already says recurse “where the platform permits it”; define platform behavior explicitly, report inaccessible descendants, and make scanning cancellable/resumable. Android SAF supports a selected subtree, but exclusions and provider-specific behavior mean users must see partial-scan failures rather than a false “all songs imported” result.
- **Medium — managed copy's lifetime and backup semantics need a choice.** Use Capacitor's durable app-private `Data`/`LibraryNoCloud`-equivalent location, never Cache. Decide whether native app backups include the library: this affects device migration and restore expectations. Local files in app-private storage are device-local, so they must be reconstructed from cloud sync or re-imported after app/device loss.
- **Medium — web `linked_origin` should be its own capability state.** Browser file handles/permissions are separate from native URIs/bookmarks and may expire or be denied. Model local availability/permission independently from origin type and copy/link mode; do not have the server interpret browser handles.

### Gaps
- The implementation plan does not name a concrete iOS/Android file-picker plugin or native bridge, nor define iOS bookmark format/lifecycle, Android persistable grant flags, folder recursion limits, or picker behavior for external/cloud-backed providers. Official platform docs explain the mechanisms but do not establish what a chosen Capacitor plugin supports.
- The plan does not state whether app-managed native songs are included in device backups or how much local storage can be reserved/managed. These are product/platform decisions.

## Are Railway bucket uploads, scoped jobs, and status/retry semantics race-safe?

### Takeaway

The presigned direct-to-bucket approach fits Railway and avoids routing audio through Gin, but the sync plan needs a concrete state machine, idempotency key strategy, checksum protocol, and native multipart implementation before it is robust. Keep one immutable cloud-object generation per audio content version, record durable per-track job items in PostgreSQL, and use an outbox/reconciliation worker to cover scope changes and deletion races. Railway's bucket feature set also limits the recovery guarantees available in the plan: it currently does not support bucket versioning or lifecycle configuration, so app-level generations and cleanup are important.

### Cited Findings
- Railway supports private S3-compatible buckets, direct client uploads using presigned URLs, presigned downloads, and multipart uploads. It explicitly states bucket egress is free, while uploads sent from a Railway service count as service egress. [Railway Storage Buckets](https://docs.railway.com/storage-buckets), [Railway upload and serving patterns](https://docs.railway.com/storage-buckets/uploading-serving)
- Railway currently lists object versioning, object locks, and bucket lifecycle configuration as unsupported. Bucket deletion is recoverable only for a 52-hour window; after that, objects are destroyed. [Railway Storage Buckets](https://docs.railway.com/storage-buckets)
- AWS S3 multipart uploads require explicit completion or abort; unfinished parts continue to consume storage. Multipart ETags are not necessarily MD5 hashes. S3 supports full-object checksums for multipart uploads and can validate them on completion. [AWS S3 multipart upload overview](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)
- AWS documents that concurrent multipart uploads to the same key can race; a later upload can become current even if an earlier upload completes afterward, and a delete during an in-progress upload can still be followed by successful object creation. S3 supports conditional writes to prevent accidental overwrite. [AWS S3 multipart concurrency and conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [AWS S3 conditional requests](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-requests.html)
- Capacitor File Transfer supports file-path upload/download and progress events, but its documented upload shape is one file path and one HTTP request. It does not specify S3 multipart part slicing, per-part resume, or S3 multipart completion. [Capacitor File Transfer API](https://capacitorjs.com/docs/apis/file-transfer)

### Inferences
- **Critical — delete can race with a started upload and resurrect cloud data.** The plan allows client-uploaded objects to finish after track deletion and says to delete the bucket object asynchronously, but no tombstone/generation check prevents an old upload grant or multipart completion from creating the object after cleanup. On delete, first tombstone the track/version and revoke logical access; have completion re-check current track generation and deletion state in a DB transaction; enqueue orphan cleanup after grant expiry plus a safety delay. Use unique immutable object keys per content generation, not one key overwritten in place.
- **High — `media_assets` per track plus `track_assets` is contradictory.** The model says “one optional cloud-backed audio asset per track” and separately lists a track-to-assets relation for “one or more encodings or versions.” Pick an MVP invariant. If only one current original encoding is supported, collapse both into `cloud_objects(track_id PRIMARY KEY, object_key, checksum, byte_size, generation, status, verified_at)`. If preserving encodings/versions is a real requirement, make `media_assets` the immutable object-version table and keep `track_assets` only as the explicit relation; document the lifecycle and current-version pointer.
- **High — upload “verification” is ambiguous.** `HeadObject` can check object existence/size/metadata, not independently establish that bytes match a client-provided checksum unless the object store validated and stored that full-object checksum. Specify algorithm and full-object checksum headers, read back the provider checksum where supported, and distinguish “transport integrity checked” from “server independently rehashed.” Do not use `ETag` as a content hash. Railway's S3 compatibility claim alone does not prove every checksum-header behavior; run an integration test against Railway before relying on it.
- **High — large-file multipart is not implementable from the described Capacitor flow without additional work.** The plan simultaneously promises native direct uploads, multipart, resumability, and short-lived grants. Capacitor File Transfer's public API does not describe S3 multipart orchestration. Either use native file streams/ranged reads via a plugin and persist upload ID/part ETags, or set an initial maximum size and use one presigned `PUT`, then add multipart after a spike. Include abort cleanup by a scheduled DB/S3 reconciliation job because Railway has no lifecycle rule support.
- **High — scope snapshot plus “sync current members” has unclear semantics.** A snapshot makes a job's membership stable, but songs/playlists can be added, removed, moved, or deleted while that job runs. Define that one job completes its accepted snapshot while a follow-up job reconciles latest scope membership; never infer current status from a stale job snapshot. Materialize work items in `cloud_sync_job_items(job_id, track_id, generation, state, attempts, error, unique(job_id, track_id, generation))`, rather than an unbounded JSON membership blob.
- **High — future scope uploads can be lost without transactional enqueueing.** The plan says future scope members auto-queue, but does not define where enqueue occurs. Write track/playlist/group membership changes and an outbox event in one Postgres transaction; worker consumes outbox idempotently. Also run periodic reconciliation of enabled scopes against current membership as a safety net. This avoids a process crash between DB commit and job creation.
- **High — a one-asset-per-track rule fails on resync or content changes.** The plan supports resync replacing a source file and mentions content version/checksum, yet one stable object key can be overwritten by two devices uploading different local generations. Add monotonic `source_generation` / immutable asset generation and only atomically promote a verified generation as current; stale jobs must not change the pointer. Start upload only from a stable snapshot of a readable local file (copy/link can change during transfer); stat before and after or stage a temporary managed copy when the source is mutable.
- **Medium — sync status lacks an unambiguous aggregate definition across scopes.** A track may be in multiple enabled scopes or a playlist may change membership while uploading. Store object readiness per track generation; compute scope status from its current membership and object readiness, while separately exposing active job progress. Define empty scope status, deleted/missing linked origin, a current track version differing from an already-ready object, and paused/failed retries.
- **Medium — direct presigned URLs are bearer credentials.** Keep expiries short (the Railway guide says presigned URL validity can be up to 90 days, which is a maximum, not a recommended duration), bind to an opaque single-use staging key and expected size/checksum when the S3 implementation permits, avoid logging/query-string capture, and do not return the long-lived bucket credentials. For mobile background/retry flows, renew expired grants rather than persisting signed URLs as job identity.
- **Medium — Railway platform constraints invalidate generic cleanup/recovery wording.** “Abandon incomplete multipart uploads through a scheduled cleanup job” is sensible because Railway lacks lifecycle rules, but define how the job discovers uploads and removes parts (`ListMultipartUploads`/`AbortMultipartUpload`) and how it handles a racing active job. A second provider backup is an essential requirement if Railway is the only cloud copy because Railway does not expose versioning/lifecycle support; object inventory/checksum scans alone detect loss but cannot restore it.
- **Medium — Capacitor transfer APIs need an adapter for presigned raw PUT.** File Transfer defaults to multipart/form-data unless content type is explicitly set; for S3 presigned PUT, use the exact signed headers and raw octet stream. Validate iOS/Android behavior for file URIs, cancellation, backgrounding, and retries. A `PUT` URL and a `POST` form presign are different protocols; the plan should choose one rather than saying generic “presigned URL.”

### Gaps
- Railway's docs state broad S3 compatibility and list multipart uploads, but do not give a detailed compatibility matrix for `ChecksumSHA256`, checksum retrieval, conditional multipart completion, or multipart-upload listing/abort behavior. Prove the exact sequence with an integration test before documenting those as guaranteed.
- Railway does not document native bucket snapshots/version recovery in the cited bucket docs. The plan correctly flags this uncertainty; recovery design must specify a provider/account-independent backup and a restore test.
- Product semantics remain unspecified for whether disabling one scope should preserve cloud copies that are no longer referenced by any enabled scope, how long deleted songs remain recoverable, and whether hard delete means erasure across offline devices. Current plan says scope disable retains assets, but no quota/free-space cleanup policy follows.

## Which data model and deletion/recovery boundaries are simplest and safe?

### Takeaway

Separate three concerns cleanly: (1) account catalog/configuration, (2) per-device playable-file state, and (3) optional cloud blob state. Keep paths and native grants exclusively local. For an MVP with one original encoding, collapse redundant cloud-asset relationships; keep explicit join tables where the product truly has many-to-many ordering (playlist items and group-playlist memberships). Make import/sync work records device-local versus server-owned explicit, and make deletion an asynchronous tombstone/outbox workflow that converges across offline devices.

### Cited Findings
- The plan already correctly says never sync absolute OS paths or device access grants; Android and Apple file access is URI/sandbox-grant based and platform-specific. [Android SAF URI permissions](https://developer.android.com/reference/android/content/Intent#ACTION_OPEN_DOCUMENT), [Apple document access requirements](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/DocumentPickerProgrammingGuide/AccessingDocuments/AccessingDocuments.html)
- Railway's buckets are private and direct presigned transfer avoids routing audio through the service, but bucket versioning and lifecycle configuration are currently unsupported. [Railway Storage Buckets](https://docs.railway.com/storage-buckets), [Railway upload and serving patterns](https://docs.railway.com/storage-buckets/uploading-serving)
- AWS S3 deletion is permanent when versioning is disabled; with versioning enabled, ordinary delete creates a delete marker and old versions remain. This is AWS S3 behavior, not a recovery promise for Railway Buckets, which do not support versioning. [AWS S3 DeleteObject behavior](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObject.html), [Railway Storage Buckets](https://docs.railway.com/storage-buckets)

### Inferences
- **High — “delete song” mixes logical deletion, local cleanup, and cloud erasure.** Separate a server-side catalog tombstone from object deletion and per-device file cleanup. Recommended sequence: transactionally tombstone track and append outbox/change-log event; reject new grants and mark active generations deleting; workers remove cloud objects idempotently; devices remove app-managed copies after receiving the tombstone (linked source files remain untouched); retain a minimal tombstone until all active sync cursors have passed or a retention window expires. Explain that an offline device may retain a local copy until reconnect. If strict erasure is promised, define an online/retention guarantee and prevent old jobs restoring the object.
- **High — “every song has provenance” should not force `track_sources` into a multi-origin abstraction prematurely.** The written import rule says each track begins from one selected origin, and Drive bytes are copied locally. MVP can keep one `origin_kind` plus provider ID/locator metadata on `tracks` or one 1:1 `track_origin` row; use a 1:N `track_sources` only if users can attach alternate origins to a song. Avoid generic provider metadata blobs with secrets or device paths.
- **High — `device_song_locations` should represent physical state only.** Treat it as a local table keyed `(track_id, device_install_id)` with `storage_mode`, durable local relative URI/path, origin handle/bookmark/permission data, local checksum/generation, health and last-check. Keep cloud readiness in PostgreSQL. `not_downloaded` is a device state, not a cloud object state; `web transient buffer` should stay in player memory. Do not mirror device location rows to the server.
- **Medium — `import_jobs` ownership is ambiguous.** Native local file scanning/copying cannot be resumed by a backend worker because source handles remain on one device; keep its queue/progress/errors in device SQLite. Google Drive import can be device-run for a local-first copy, or server-run if the app explicitly chooses server-side Drive access; choose one owner. Avoid one generic jobs table implying the server can access private device files.
- **Medium — `cloud_sync_settings` may be unnecessary for first release.** The plan says cloud is opt-in per explicit scopes, while a user-level default for future imports outside a scope is listed but has no corresponding UX. Remove this table until there is a setting that changes behavior; saved `cloud_sync_scopes` plus per-object readiness are sufficient for the described feature.
- **Medium — avoid duplicating “sync status” in scope, job, and asset records.** Keep authoritative object status/generation on cloud-object rows and retry/progress on job items; derive scope indicator from current scope membership. Store only user-managed scope enablement in `cloud_sync_scopes`. This prevents disagreement between several status fields.
- **Medium — content-hash deduplication needs a privacy/product boundary.** The plan suggests content hashes may find exact duplicate files. Do not use a global hash uniqueness key across users: it can leak whether another user has a song and complicates ownership/deletion. If deduplicating, scope it per account or use an internal blob table with strict tenant authorization and a separate ownership reference count; simplest MVP is no cross-user dedup.
- **Medium — delete/recovery and incremental sync need one consistent change protocol.** `change_log` alone is not sufficient unless every mutation and outbox publication is atomic. Use monotonic per-user change cursor plus tombstones for track, playlist, group and membership deletion; client applies idempotently, and API checks ownership at fetch/grant time. Define conflict behavior for concurrent reorder operations (version/ETag optimistic concurrency with last-write-wins or explicit conflict response).
- **Low — `groups` and `playlists` semantics are reasonably normalized.** Keep `group_playlists` (many-to-many and ordered) and `playlist_items` (ordered song membership) because they represent distinct product relationships. An Artist page is a query over `tracks.artist_id`, not another collection table. Saved filter booleans belong in a compact user preference record and can be merged as one preference update, not per-device rows.

### Gaps
- The plan does not define ownership/deletion policy for linked songs when one device deletes a track, whether cloud removal must be immediate or delayed, or how stale/offline devices receive cleanup tombstones.
- “One song” identity across duplicate imports, different encodings, edits, and resync is unresolved. The current content-hash suggestion does not define whether same bytes should merge catalog identity or merely provide a duplicate warning.
- The cloud backup provider/account, retention period, disaster-recovery RPO/RTO, and quota cleanup policy are still decisions. A second copy recommendation exists, but not its operational design.
