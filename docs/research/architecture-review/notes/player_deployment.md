# Player lifecycle and deployment review

Research checked against the current Markdown plan and its HTML companion on 2026-10-06. External sources below are official documentation (React, MDN, Apple, Android, Vercel, Railway); access date is 2026-10-06. Findings are ranked by implementation risk.

## React player lifecycle, queue, and native background playback

### Takeaway
The plan correctly keeps the mini-player and full Playing screen attached to one app-level playback session, but it leaves the actual playback owner ambiguous. React route-level state is sufficient to keep a web player mounted across navigation; it does not itself provide native background playback. Define one playback interface and make the native audio engine/service authoritative on mobile, with React rendering/subscribing to it. Specify a few missing queue transition rules before implementation.

### Cited Findings
- The plan states that the controller/media element lives above route-level pages, and that mini-player and Playing screen observe the same state and media instance. This is a good single-web-player rule, but it specifies only client UI lifetime and not recovery on app/WebView lifecycle changes. [Implementation plan](../../../implementation-plan.md) (reviewed 2026-10-06).
- React describes Context as a way to let components read values supplied by a provider; it does not supply a durable process, media engine, or external playback lifecycle. React's documented `useSyncExternalStore` is the suitable bridge when React needs to subscribe to a state store outside React and receive immutable snapshots. [React `createContext`](https://react.dev/reference/react/createContext), [React `useSyncExternalStore`](https://react.dev/reference/react/useSyncExternalStore) (accessed 2026-10-06).
- Apple's default audio session silences playback when the iOS device is locked. For media playback that should continue while locked or in another app, Apple documents configuring `AVAudioSession` with the playback category and enabling the Audio, AirPlay, and Picture in Picture background mode. Apple also documents observing/handling interruptions; AVPlayer can pause when an interruption occurs. [Apple: Configuring your app for media playback](https://developer.apple.com/documentation/avfoundation/configuring-your-app-for-media-playback), [Apple: Handling audio interruptions](https://developer.apple.com/documentation/AVFAudio/handling-audio-interruptions) (accessed 2026-10-06).
- Android's recommended background-playback architecture places the `Player` and `MediaSession` in a `MediaSessionService` separate from the Activity; the OS/system controls and other clients can control it while UI is absent. The service also has explicit lifetime/release behavior and playback-resumption considerations. [Android: Background playback with a MediaSessionService](https://developer.android.com/media/media3/session/background-playback), [Android: MediaSessionService API](https://developer.android.com/reference/androidx/media3/session/MediaSessionService) (accessed 2026-10-06).
- Capacitor Background Runner is an event-based headless JS environment for scheduled/background tasks; its documentation says runner contexts are short-lived, state is not maintained between calls, and the platform does not allow persistent always-running background services through this API. It is therefore not a native media player or substitute for iOS audio-session/Android MediaSession playback architecture. [Capacitor Background Runner](https://capacitorjs.com/docs/apis/background-runner) (accessed 2026-10-06).
- The web platform can expose media metadata and hardware/lock-screen actions through `navigator.mediaSession`, but MDN marks the API as limited availability. It should be progressive enhancement, not a cross-browser playback guarantee. [MDN: Media Session API](https://developer.mozilla.org/en-US/docs/Web/API/Media_Session_API) (accessed 2026-10-06).

### Inferences
- **High severity — One player owner per platform is missing.** Keep a common UI-facing `PlaybackController` contract (load/play/pause/seek, queue commands, state/events); implement a web adapter with one long-lived `HTMLAudioElement` and a native adapter backed by a native player. On iOS, use the native audio session/background mode; on Android, use a Media3 player in one `MediaSessionService`. The Capacitor bridge sends commands and receives events. React holds presentation state and subscribes to snapshots; native audio does not depend on the React component or WebView staying alive. This resolves the conflict between “shared React app” and native background playback without forcing one media implementation to cover unlike lifecycle requirements.
- **High severity — Native lifecycle requirements are underspecified.** Do not define “background playback complete” as merely continuing across lock. Include remote/lock-screen/headset play-pause/seek/previous-next controls, audio focus/interruptions, route changes (headphones unplugged/Bluetooth), notification/metadata, resume policy, service cleanup, and tests for app process/UI recreation. These are platform-player responsibilities, surfaced to the shared UI through the adapter.
- **Medium severity — Queue transition rules are incomplete.** The plan says queues start from the current view order, shuffle randomizes while preserving the current song, previous/next disable when no adjacent queue item exists, and repeat turns off when the current track changes. It does not define what “previous” means near the start, what happens at queue end, whether end-of-track auto-advances, how a shuffled queue avoids repeats, or how manual song selection and queue-source mutations interact. Recommendation: snapshot a transient queue when play starts; keep the current song fixed when shuffling, shuffle only unplayed upcoming IDs once, and keep Previous/Next at boundaries disabled as the screen already suggests. Natural end advances to next if present, otherwise stops; repeat-one replays the same ID without turning off, while any command that changes the current ID resets repeat. Define how deleting the current/queued track removes it and moves/stops playback. Make queue transitions a small pure reducer shared by adapters and cover it with table-driven tests.
- **Medium severity — “Repeat turns off if song changes” needs a precise distinction.** Repeat-one reaches the end and seeks/restarts the *same* track; that is not a track change. Reset repeat on a transition to a different track ID, not on media-element ended/reload events for the same ID.
- **Low-to-medium severity — Backend playback responsibility may be extra coupling.** The backend module list includes “playback,” although the documented audio path is local client playback and the API only needs to authorize cloud asset URLs/status. Unless the product adds listening history, remote control, or transcoding, remove a separate Gin playback domain. Keep queue/player behavior in the client adapters and use the API for catalog, sync jobs, and scoped object grants only.

### Gaps
- The plan does not select a concrete Capacitor-native playback plugin/library or say whether a custom Capacitor plugin will be required. The official Capacitor core plugin list does not define a general media playback service; this needs a small technical spike on iOS and Android before promising background playback. [Capacitor official plugin list](https://github.com/ionic-team/capacitor-plugins) (accessed 2026-10-06).
- The plan does not say whether queue/current position/shuffle choice survive a process restart. Decide whether restart restores only the last track/position or the whole queue; native playback can outlive the UI, so the bridge needs reconnection and snapshot behavior.

## Web full-track loading, Blob lifecycle, and storage limits

### Takeaway
Loading only the selected cloud-backed song as one Blob matches the stated web constraint and avoids sending the library to the browser. It still downloads and retains one complete track before playback starts, so this cannot safely ship with size/duration limits deferred. Make a hard admission limit and cancelable bounded fetch part of the first web playback release; use OPFS only for explicitly downloaded offline tracks and explain browser persistence limits.

### Cited Findings
- The plan says web fetches a complete selected track into one active Blob-backed resource, starts only after fetch completion, does not prefetch, revokes the old object URL on switch, and defers size/duration thresholds. It also recognizes browser memory pressure and OPFS quota/eviction concerns. [Implementation plan](../../../implementation-plan.md) (reviewed 2026-10-06).
- MDN defines Blob as immutable raw data, supports Blob size, and distinguishes `Blob.arrayBuffer()` which creates an ArrayBuffer containing all Blob contents. That supports avoiding an additional whole-file ArrayBuffer copy, but does not promise a particular browser backing-store or memory behavior for a Blob. `URL.createObjectURL()` creates a URL pointing at a Blob, and `URL.revokeObjectURL()` releases the URL reference; MDN explicitly calls out leak potential in a different context (service worker API unavailable because of memory leaks). [MDN: Blob](https://developer.mozilla.org/en-US/docs/Web/API/Blob), [MDN: URL.createObjectURL](https://developer.mozilla.org/en-US/docs/Web/API/URL/createObjectURL_static) (accessed 2026-10-06; Blob page last modified 2026-09-11).
- Browser storage is best-effort by default. MDN documents that origin data can be evicted under storage pressure, total-browser storage pressure, and proactively for unused origins in Safari; `navigator.storage.persist()` may be requested but is not a universal guarantee. [MDN: Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) (accessed 2026-10-06).
- Browsers can block audible media autoplay until the user interacts with the page, and `HTMLMediaElement.play()` can reject when autoplay is blocked. Loading a Blob from a click is user-initiated, but later queue auto-advance may still encounter browser-specific behavior and needs error handling. [MDN: Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay) (accessed 2026-10-06).
- Railway says bucket egress is free; serving via a presigned URL sends object data directly from the bucket and avoids Railway service egress. Proxying the object through a service incurs service egress. [Railway: Uploading & Serving Files](https://docs.railway.com/storage-buckets/uploading-serving) (accessed 2026-10-06).

### Inferences
- **High severity — Deferring web size and duration thresholds leaves unbounded per-play memory/network use.** The plan says “thresholds later” while making a full-file Blob mandatory. A long/high-bitrate file on a low-memory mobile browser can consume a large allocation and delay initial audio until the entire download completes. Before first web playback release, choose configurable maximum bytes and duration (plus supported formats), store object byte size/duration at import, reject/offer explicit offline download above the web-play cap, and enforce a byte cap while reading the response stream rather than trusting `Content-Length` alone. Use `AbortController` and a monotonically increasing load token so rapid track changes cancel the previous transfer and stale responses cannot replace the requested track. Start with a conservative cap and measure representative iOS Safari/Android Chrome/desktop memory and time-to-play.
- **Medium severity — Explicit lifecycle cleanup is correct but should be a state transition, not component cleanup.** A single web media controller owns the active object URL and Blob; on accepted track switch, abort fetch, pause, detach prior source, clear references, revoke URL, then fetch the next. Clean up on sign-out/session end and fatal decode/network error. Avoid revoking as soon as play starts because the media element still needs the Blob URL; revoke after source detach/track completion/switch.
- **Medium severity — The browser download and playback flow should use a private presigned bucket URL directly.** The current plan already does this. Keep API authorization before minting a per-object short-lived URL; direct fetch avoids sending the audio body through Gin/Vercel and Railway service egress. Ensure bucket CORS permits the deployed web origins and exposes the headers the bounded downloader needs; never put storage credentials into Vite/browser config.
- **Medium severity — Offline web storage must be treated as a disposable local cache.** OPFS/IndexedDB audio can be evicted or cleared; do not present web “Download for offline” as an independent backup. Use `navigator.storage.estimate()` and (where supported) `persist()` as advisory signals, detect quota errors, and always allow redownload from a verified cloud asset. State clearly that cloud sync is needed to restore after browser data loss.
- **Medium severity — Blob full-fetch imposes a product-level latency tradeoff that cannot be optimized away without changing the decision.** Show download progress, cancellation, expected size, and a loading state; retain exactly one current Blob; clear it on track change. Keep the behavior as asked (whole song before playback, no streaming) but document that web is network-only for cloud tracks unless they were explicitly downloaded offline.
- **Low severity — File source is different on web.** As the plan says local-only files do not transfer cross-device: a browser can play a local `File` chosen/imported in that same browser if the selected file handle remains valid, but generally must not assume it can recover an arbitrary OS path later. Keep browser local import/relink behavior separate from Capacitor native file URIs and from cloud playback.

### Gaps
- The plan sets no proposed initial size/duration cap, file-format allowlist, low-memory device baseline, or “too large for web” UX. These are product and test decisions; browser APIs do not supply one universal safe limit.
- The plan does not specify media content type/length metadata served by the bucket or how the client handles missing/incorrect object length, expired URL during full fetch, CORS failure, unsupported codec, or a failed `audio.play()` promise.

## Vercel/Railway responsibilities and deployment simplification

### Takeaway
The service boundary is mostly sound: Vercel serves the Vite client; Railway runs Gin, PostgreSQL, bucket storage, and any asynchronous worker. Keep all song bytes off Vercel Functions and avoid a backend proxy for routine song downloads. The main simplification is to delay/separate workers until real durable background jobs exist, and use Railway workers only for verification/retries/maintenance—not direct object delivery when clients can use signed bucket URLs.

### Cited Findings
- The plan assigns the React/Vite web client to Vercel and Gin, PostgreSQL, workers and optional Railway Bucket to Railway; it correctly says Vite `VITE_*` values are public and should not contain signing/bucket/auth secrets. It documents client-to-bucket presigned transfers and a separate worker. [Implementation plan](../../../implementation-plan.md) (reviewed 2026-10-06).
- Railway's private S3-compatible bucket supports direct presigned upload/download. Bucket egress is free; service egress is billed, and routing bytes through a service incurs that service egress. [Railway: Uploading & Serving Files](https://docs.railway.com/storage-buckets/uploading-serving), [Railway Storage Buckets](https://docs.railway.com/storage-buckets) (accessed 2026-10-06).
- Vercel Functions have a documented maximum 4.5 MB request or response payload. The plan deploys a static Vite application and does not need Vercel Functions for audio; this limit matters only if someone later adds an audio proxy/upload API route on Vercel. [Vercel: Function limits](https://vercel.com/docs/functions/limitations) (last updated 2025-12-18; accessed 2026-10-06).
- Railway documents worker/background services as separate services, while the plan's cloud-sync rows/jobs are PostgreSQL-backed durable records and direct client-to-bucket transfers. [Railway: Cron jobs, background workers, and queues](https://docs.railway.com/guides/cron-workers-queues), [Railway: Uploading & Serving Files](https://docs.railway.com/storage-buckets/uploading-serving) (accessed 2026-10-06).

### Inferences
- **High severity — The worker/job boundary needs one explicit durable execution model.** PostgreSQL `cloud_sync_jobs` is described as durable, but no queue/claim/lease/heartbeat/retry/dead-letter mechanism is specified. Don't add Redis or a queue service up front: for an initial one-worker deployment, let a worker claim Postgres job rows with bounded leases/attempt counts, idempotent per-track tasks and backoff; use a transactional outbox/DB job insert alongside scope changes so work cannot be lost between commit and enqueue. Move to a broker only after measured concurrency/latency warrants it. The API should return accepted job IDs/status, not wait for uploads or scans.
- **Medium severity — Separate worker runtime is justified only for durable/background work.** Direct uploads/downloads are performed by the client and presigned URLs are minted by Gin, so worker processes are not upload relays. In the planned first releases, defer operating a separate worker until scoped sync/reconciliation jobs ship; then keep it private and narrowly authorized to inspect/verify/checksum/delete bucket assets, retry jobs and reconcile object inventory. It should not have a public domain.
- **Medium severity — Remove routine media bytes from the Gin and Vercel request path.** For cloud web playback, the API should authorize a track and issue a short-lived object-specific GET grant, and the browser fetches the Railway bucket itself. For sync, browser/native client uploads and native downloads likewise go directly to the bucket. This avoids Vercel's function payload limit and Railway service egress, and prevents loading large assets into API memory. Never accept a user-supplied bucket key without resolving/authorizing it from the owning database record.
- **Medium severity — Clarify the phrase “system saves those files” during import.** Local-first import initially only records local catalog/provenance and device-local location; PostgreSQL gets catalog metadata when online; bucket receives no bytes until explicit cloud sync. Keep three named operations distinct in API and UX: import/index locally, upload to cloud, download to this device. This avoids accidental audio uploads or assuming a Drive/source import is already restorable from another device.
- **Low severity — Keep Vercel preview storage CORS controlled.** Only stable intended production/staging/Capacitor origins should be permitted on the private bucket, and signed URLs remain bearer tokens. Avoid broad wildcard preview origins for a private user library; provide a stable staging host or test downloads through a staging client. Keep cross-origin policy separate for Gin and bucket, as the plan already notes.

### Gaps
- Railway's current worker guide and storage docs support separate worker deployment and direct signed file delivery, but this review did not validate current plan-specific pricing, replica counts, or data durability/SLA terms; those should be rechecked before launch because they vary over time.
- The plan does not identify a single responsibility owner for object integrity: currently API or worker can `HeadObject`, while a trusted worker may read/hash bytes. Prefer one documented worker verification path after client upload completion, with client checksum as an expected value and server/worker verification before marking the asset ready.
