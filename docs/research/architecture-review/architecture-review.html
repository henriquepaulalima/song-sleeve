Simplify Song Sleeve Before Building It

Current design decisions (2026-10-07): checklist items 1–4 are resolved in the implementation plan. Every track, synced or unsynced, has one authoritative current metadata/source document. Unsynced external file changes affect device health only; manual source confirmation refreshes the document. All accepted app edits are account-level and apply to other devices at their next online app open, including unsynced tracks. Source replacement preserves track identity; file-derived name/artist remain suggestions until accepted. Item 3 now also defines explicit unsync: confirm scoped removal of cloud audio and managed mirrors, preserve track documents as needing a source, offer local-file selection or track deletion, and suppress automatic reupload. Offline-device cleanup runs when the device next reconnects. Item 4 fixes track identity for the document’s entire lifecycle: IDs themselves are immutable; replacement deletes the old content entity and creates a new one, then replaces the reference in the same track document. Every explicit source-file submission does this even for identical files/checksums; no duplicate-file detection or reuse is required. Network retries retain their operation identity. Item 5 now requires one server sync operation per user/track, replayable completion notifications to every device, and deferred local replacement/removal for currently playing resources with an update notice. Transfer recovery mechanics remain open. Item 6 now requires live server acceptance for all account/library changes, including local-only tracks; disconnected edits fail without application or offline replay. Cached browsing and local playback remain available. Concurrent online writes still need server revision checks, and lost responses need request-status recovery; tenant constraints and delivery details remain open. The original offline-write/replay recommendations below are superseded by the online-only changes policy. Item 7 now defines a route-independent Device Sync Service with live events and native APNs/FCM wake-ups/background transfers, so minimized devices reconcile while OS execution is permitted and catch up after deferral. Platform feasibility tests remain for implementation. See background synchronization. Synced installed playback always uses local Songs, and web loads one accepted cloud song at a time. The findings below are the original review snapshot; use the current track-document rules and remaining checklist for current decisions. Item 8 now has user-approved, inclusive per-song limits of 30 minutes AND 128 MiB across all clients/sources; implementation/resource tests remain open. See approved song limits. Item 9 now defines a 30-day opaque revocable session, email reset/logout-all, and a non-cancellable hard-deletion worker with user-last deletion and restricted post-logout device-cleanup receipts. Offline-device and backup physical-erasure limits are explicit; implementation tests remain pending. See account lifecycle. Item 10 is resolved: optional user-assigned artists, manual playlists of songs, and manual non-recursive groups of playlists are the complete organization model; Library type visibility is a display preference. Superseded organization proposals have been removed from these review materials.

The architecture has a sound product center—one account library, local-first playback, optional cloud copies, and playlists/groups as metadata—but it is not yet safe to implement as written. The main risks are mismatched meanings for a “track” versus its source, local copy, and cloud asset; cloud upload/delete races; and device-local file access treated as if a path were durable across platforms. The design can become substantially simpler by keeping a single modular Gin application, a PostgreSQL catalog, a device-owned local file index, and an optional versioned object store, with only two explicit many-to-many relationships: playlist-to-track and group-to-playlist. Before implementation, settle content-version and delete semantics, scope-sync behavior, mobile picker/player capabilities, authentication token transport, and browser playback limits. Worker scaling and richer conflict handling can be considered after the core flows work; organization stays limited to explicit artists and manual playlists/groups.

Separate catalog identity from files and device state

The current model uses “track,” “source,” “location,” and “asset” to describe several overlapping facts. tracks are stable library entries, track_sources are portable origin provenance, device_song_locations are local playable references, media_assets are optional cloud copies, and track_assets may represent multiple encodings or versions. But the plan also says there is one optional asset per track, while the relation permits multiple assets, and it does not say whether a replacement file changes a track or creates a new version. This ambiguity affects resync, duplicate imports, multi-device sync, deletion, and what a “synced” badge promises. (Markdown data model, Railway object-storage flow)

The Markdown and HTML companions are not fully in sync. The Markdown data table defines cloud_sync_scopes as the user’s durable library/group/playlist opt-in and says cloud_sync_jobs contains a membership snapshot and per-track progress; the HTML table omits cloud_sync_scopes, instead gives cloud_sync_settings a broader “user opt-in, upload scope, and auto-upload” role, and does not specify job snapshot/items. The HTML tracks row includes nullable artist_id, while Markdown lists it separately as tracks.artist_id; that difference is harmless if intentional, but the cloud-scope mismatch changes the model. Make Markdown the source of truth and regenerate or reconcile the HTML after architectural decisions. The HTML also shows the new palette as swatches, while its overall guide chrome remains on the earlier green/lime theme; this is a visual consistency issue rather than a runtime architecture blocker. (Markdown data model, HTML data model)

High priority before schema work: define a stable logical track and an immutable content_version (or file-version row) with checksum, size, media type, and generation. Each device separately records whether it has a managed local copy or a linked origin for that version. Cloud readiness belongs to a cloud-object row for that exact version. A resync that changes bytes creates a new version and promotes it only after validation; an older upload cannot overwrite the current object. For the first release, support one current original encoding per track and defer alternate encodings. Keep provenance only where useful across devices—such as a Drive file ID—and never put device paths or access grants in PostgreSQL. Android SAF references need persisted URI permissions, and Apple document access uses security-scoped references/bookmarks rather than a portable bare path; generic Capacitor Filesystem support does not provide those permission lifecycles. (Android document access, Apple document access, Capacitor Filesystem)

Use exact content hashes for integrity and duplicate suggestions, not silent title-based merging or global cross-user deduplication. A duplicate import should preserve an explicit user-visible choice: reuse an existing library entry and attach this device’s location, or create a separate track. The same policy must apply when another device imports identical bytes. Add user_id to every tenant-owned row and enforce composite foreign keys across tracks, artists, memberships, sync scopes, jobs, and cloud objects. The plan currently calls out a same-user artist reference but not equivalent constraints for other relationships. PostgreSQL composite foreign keys and unique constraints can enforce tenant and membership rules centrally, while handlers still perform authorization checks. (PostgreSQL table constraints, PostgreSQL constraints)

The clean MVP catalog is users/sessions, tracks, optional artists, playlists, playlist_items, groups, group_playlists, one account-level library-view preference, sync scopes, cloud-object versions, durable sync jobs/items, and a change/outbox log. Keep playlist_items and group_playlists: they encode real many-to-many relationships with independent ordering. An Artist page is a query over tracks.artist_id, not another collection model. The approved organization is explicit artist assignment, manual playlists of tracks and manual groups of playlists. Users create collections and their memberships; groups cannot contain groups or direct tracks. Keep the Library type visibility preference, and remove unrelated collection/settings models such as cloud_sync_settings. (Organize music, PostgreSQL unique and partial indexes)

Keep the backend modular, transactional, and small

Gin is a suitable HTTP framework, but it should own routing, input binding, middleware, and HTTP error translation—not business rules. Keep one Go modular monolith with three application modules: Account for registration, verification, sessions and profile; Catalog for tracks, artists, playlists, groups, preferences, ordering and change reads; and Media for object grants, cloud sync scopes, per-version asset state and cleanup. A small infrastructure layer owns PostgreSQL queries, email provider, platform-neutral object storage adapter, and device sync. Local file access, import scanning, metadata editing before submission, playback, and local reconciliation belong to each client because only that device can access its picker handles and app-private files. Avoid separate “artist,” “playlist,” “group,” or “playback” services; these operations share catalog transactions, and no server-side playback responsibility exists in the stated product. Gin documents middleware and binding as HTTP concerns, and specifically cautions against launching background work with the request context. (Gin middleware, Gin binding, Gin goroutines)

Persist work before returning success. Registration should transactionally create the unverified account, hashed one-time token, and email-outbox row; a worker sends/retries mail. A confirmed sync scope should transactionally persist scope state, a durable job, materialized job items, and a change/outbox event. Catalog membership changes should enqueue additional work for enabled scopes in the same transaction. A single PostgreSQL-backed worker queue is adequate initially; FOR UPDATE SKIP LOCKED supports queue-like claiming, so Redis or a broker is not an MVP requirement. Add leases, retry count/backoff, idempotent completion, and periodic reconciliation so a worker crash cannot strand a job. (PostgreSQL queue-oriented locking)

Offline writes need a clear replay contract. Assign each client mutation an operation ID and device-install ID, store a unique receipt, and make import, artist creation, membership changes, and reorder retries idempotent. Give each independently ordered collection a revision; accept reorder only against the expected revision, return a conflict for stale writes, and query with ORDER BY position, id. Publish mutations and monotonically ordered per-user change cursors in the same transaction. This is simpler to reason about than promising vague “eventual sync”; PostgreSQL does not guarantee row order without ORDER BY, and concurrent serializable work can require transaction retries. (PostgreSQL SELECT ordering, PostgreSQL transaction isolation)

The authentication flow needs launch decisions, not just endpoint names. Define browser refresh-token transport (prefer a Secure, HttpOnly, SameSite cookie with CSRF protections if cookie-based), native secure storage, access-token lifetime, refresh rotation and reuse detection, current-session identity, password reset/change, email change, and account deletion. RFC 9700 recommends sender-constrained refresh tokens or rotation for public clients and replay detection; even if the app is not implementing OAuth formally, this is a useful conservative standard for a web/native client pair. Do not issue a session until verification succeeds, and invalidate prior verification tokens when resending. (RFC 9700 §4.14)

Make sync a versioned state machine, not a badge

The current scoped design is a good UX foundation: users opt in from Songs, Playlist, or Group; a group resolves to a deduplicated union of its playlist songs; overlapping scopes share a cloud copy; future members are queued; disabling a scope does not delete bytes. Its weakness is that a saved scope, job snapshot, job progress, and asset state do not have precise separate meanings. One JSON-like membership snapshot is not enough to recover a partial job or reconcile edits made while it runs. Model cloud_sync_scopes as only the user's continuing opt-in, cloud_sync_jobs as an execution attempt, cloud_sync_job_items as durable per-track-version work, and cloud_objects as verified readiness of a specific immutable content version. Define Synced as every track in the current resolved membership having a ready object for its current version; derive the indicator from membership and object readiness, while displaying active job progress separately. (Cloud sync flow, Railway bucket flow)

Critical race to close before implementation: a delete can occur after the client receives an upload grant but before the upload or multipart completion finishes. If cleanup runs first, the old upload can recreate the object. Tombstone the track/version and revoke new grants transactionally; completion must re-check that the version is still current and not deleted; use opaque keys per immutable generation; and schedule orphan cleanup after grants expire, with a safety window. For normal song deletion, immediately remove it from catalog queries and reject new playback grants, enqueue cloud deletion, and send a tombstone through the device change cursor. Offline devices cannot erase local managed copies until they reconnect; linked source files must remain untouched. If “delete” promises immediate erasure everywhere, that promise needs a retention and offline-device policy. Railway documents that bucket versioning and lifecycle configuration are unsupported, strengthening the case for application-level generations, cleanup, and a separate backup before cloud data is a user's only copy. (Railway Storage Buckets, AWS multipart races and completion)

Do not overwrite one object key on resync. Each upload gets an upload-attempt ID, expected size and checksum, grant expiry, and immutable version key. A client “upload complete” call is a claim: verify existence and size, and define the checksum guarantee precisely. Do not treat multipart ETags as SHA-256; Railway's compatibility docs do not prove all checksum APIs behave identically, so test the exact checksum/complete/abort sequence against Railway. Capacitor File Transfer covers file-path transfers but does not specify multipart part slicing, resumable state, or orchestration. To reduce risk, start with an explicit maximum size and one raw presigned PUT; add multipart only after proving the native adapter and cleanup path. A generic claim of “resumable upload” is not sufficient. (AWS S3 multipart uploads, Capacitor File Transfer, Railway bucket upload/serving)

The feature boundaries should stay explicit: import/index locally, upload to cloud, and download to this device are different operations. Drive selection results in bytes copied to the device's Songs directory; it does not mean the bucket already has a copy. Local scanning/import progress belongs in device SQLite; cloud upload jobs belong on the server. Gin grants short-lived object-specific URLs but never proxies audio, and Vercel serves only the web client. Direct bucket transfer avoids loading song bytes through application servers, but the signed URL is a bearer credential: keep it short-lived, never log it, and renew it on retry. (Railway direct upload/serving, Vercel function limits)

Respect platform playback and file-access limits

The shared React player bar and Playing screen can remain common UI, but React route state is not a native audio service. On web, one long-lived HTMLAudioElement and controller can survive navigation while the app remains open. On mobile, the audio engine must be owned by a native playback adapter/service that can continue when the WebView is backgrounded or absent; React should subscribe to snapshots and issue commands. Android's Media3 guidance uses MediaSessionService; iOS background playback requires audio-session/background-mode configuration and interruption handling. Capacitor Background Runner is short-lived task execution, not an always-running media service. The plan's “background playback and lock-screen controls” therefore needs a technical spike before it becomes a delivery promise. (Android MediaSessionService, Apple media playback configuration, Capacitor Background Runner)

The queue needs explicit transition rules: snapshot the ordered IDs when playback starts; shuffle only upcoming songs while keeping the current song fixed; define end-of-queue and previous-at-start behavior; and decide what happens if the current or queued song is deleted. Repeat-one should replay the same track without resetting; reset repeat when the current track ID changes. The plan currently says repeat turns off on song change but does not specify natural end/reload semantics. Put transitions in a small pure queue reducer and test its boundaries. The native adapter must also handle lock-screen/headset controls, audio focus/interruption, route changes, service lifecycle, and reconnecting UI after process recreation; MediaSession APIs provide these system integration points. (Android MediaSessionService, Apple interruption handling)

For browser cloud playback, the chosen whole-track Blob model limits simultaneous files but does not bound a single file's memory or wait time. The implementation plan explicitly defers size and duration thresholds; that is incompatible with shipping full-file fetch without a cap. Set a byte limit and supported-format policy before web playback, store file size/duration at import, enforce the byte cap while reading (not only from Content-Length), show progress/cancel, abort stale loads on rapid track changes, and test low-memory mobile browsers. Keep one active Blob URL and revoke it after detaching the media source. OPFS is best-effort browser storage and can be evicted, so offline web download is a recoverable cache, not the sole backup. (MDN Blob, MDN object URLs, MDN storage eviction, MDN autoplay)

Resolve the blockers, then add features in stages

The architecture decision gate before schema/code is compact: choose one current audio version model and duplicate-import behavior; define cloud deletion, offline tombstones, scope removal and restore semantics; choose a mobile file-picker/access bridge and native playback implementation; set the initial browser full-track size limit; and choose auth credential storage/refresh behavior. These choices define data ownership and irreversible user expectations. Organization scope is now fixed to user-created playlists of songs, groups of playlists and explicit artist assignments. A schema diagram and migration/index list should reflect these decisions before implementation starts.

After that gate, build one end-to-end vertical slice: verified account and one session; local import into copy mode; one track with optional artist; playback in web and native foreground; a manual playlist; then device-local persistence/relink. Next add link mode with platform grants, offline mutation replay and ordering revisions, followed by opt-in cloud upload/download with immutable versions, a PostgreSQL-backed worker, object cleanup, and delete tombstones. Add web offline cache, multipart transfer, richer conflict resolution, cross-provider backup automation, and worker/broker scaling only when the MVP's limits or usage justify them. This sequence verifies the hardest boundaries without committing to premature microservices or queue infrastructure.

Conclusion

The most useful simplification is to treat catalog metadata, device file access, and cloud object versions as three different state owners. That model keeps local paths private, gives “synced” a testable definition, and makes replacement/deletion races manageable. The app can remain a simple modular monolith at first, but mobile background playback, browser file limits, and destructive cloud lifecycle choices are real platform/product constraints that should be resolved with focused spikes and explicit semantics before they are hidden inside implementation details.
