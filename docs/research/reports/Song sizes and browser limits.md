# Browser limits shape whole-song playback choices

**Research date:** 2026-10-07. **Status:** research completed; the user approved a per-song limit of 30 minutes AND 128 MiB on 2026-10-07, applied across all clients and sources. Implementation/resource tests remain pending.

**Modern Chrome, Edge, Firefox, and Safari can conditionally store a single 128 MiB song; none guarantees that every device can safely fetch and play it.** Ordinary 3–5-minute compressed music needs about 2.88–12 MB, while a 30-minute 320 kbps track needs 72 MB. Uncompressed and high-resolution files increase those sizes substantially. Browser disk quota, temporary Blob backing, playback memory, and codec support are separate constraints. The user has approved **30 minutes AND 128 MiB** as the per-song admission limit across web, mobile, desktop, local imports, source replacements and cloud sync. Both inclusive checks must pass; this is a product rule, not a browser safety promise. The current full-download-before-play architecture remains intact. Over-limit songs are rejected rather than admitted through a native-only exception. See the [current enforcement policy](../../implementation-plan.html#approved-song-limits).

## Ordinary songs need megabytes; longer WAV files need hundreds

Use **3–5 minutes** for ordinary-song fixtures, **10–30 minutes** for extended-song fixtures, and **60 minutes** as a stress case. Chartmetric's original 2024 report places its most common chart-appearing Spotify tracks between 2:51 and 3:09 and includes a 73-minute mixtape. These observations support a popular-music baseline but do not establish a universal average for mixed personal libraries. The actual collection will be a better source for later percentile-based policy. ([Chartmetric Year in Music 2024](https://reports.chartmetric.com/2024/chartmetric-year-in-music-2024))

Calculated payload is `seconds × encoded bits/second ÷ 8` for constant or actual average bitrate, and `seconds × sample rate × bits/sample × channels ÷ 8` for PCM. **MB means 1,000,000 bytes; MiB means 1,048,576 bytes.** The values below exclude embedded metadata, embedded artwork, headers and padding; inspect actual file length for admission. Fraunhofer documents MP3 through 320 kbit/s, Apple uses 256 kbps AAC in its Digital Masters tools, and the FLAC standard describes ordinary CD PCM as stereo 16-bit/44.1 kHz. These are useful encoding benchmarks, not universal file parameters. ([Fraunhofer MP3 and AAC](https://www.iis.fraunhofer.de/content/dam/iis/de/doc/ame/conference/AES-17-Conference_mp3-and-AAC-explained_AES17.pdf), [Apple Digital Masters](https://www.apple.com/apple-music/apple-digital-masters/), [RFC 9639](https://www.rfc-editor.org/rfc/rfc9639.html))

| Duration / encoding | Audio payload MB | Audio payload MiB |
| --- | --- | --- |
| 5 min, 128 kbps | 4.80 | 4.58 |
| 5 min, 256 kbps | 9.60 | 9.16 |
| 5 min, 320 kbps | 12.00 | 11.44 |

| 5 min, stereo PCM WAV 16-bit / 44.1 kHz | 52.92 | 50.47 |

A 30-minute compressed song can be smaller than a five-minute high-resolution WAV. FLAC losslessly compresses PCM but has **no fixed guaranteed bitrate or compression ratio**; different signals compress differently. Measure its actual bytes rather than assume a universal fraction of WAV size. Filename extensions also do not establish sample rate or container contents. These differences require independent duration, byte-size and codec checks. ([FLAC bitrate FAQ](https://www.xiph.org/flac/faq.html#general__lowest_bitrate))

## Every modern major browser has conditional single-file storage

The matrix describes API capability, **not device measurements**. OPFS stores private files for the web origin, under HTTPS, and shares the origin's quota; it does not create a visible device `Songs` folder. Use OPFS for explicit web copies/downloads and IndexedDB for catalog/index records. Transient cloud playback retains only the selected complete Blob and object URL; it does not automatically create an offline copy. ([Google OPFS guide](https://web.dev/articles/origin-private-file-system))

| Browser / platform | OPFS availability and writer | One 128 MiB file | What is unsupported or needs a fallback |
| --- | --- | --- | --- |
| Chrome desktop | Root/read and async writer from 86; worker writer from 102 | Conditional support | Older APIs, unavailable storage, insufficient space, or unsupported codec |
| Edge desktop (Chromium) | Compatibility follows Chromium; detect actual APIs | Conditional support | Same runtime restrictions; quota is not playback memory |
| Chrome Android | Root/read and both writers from 109 | Conditional support; device tests required | Older versions; low resources; original picker depends on version |
| Edge Android (Chromium builds) | Detect bundled engine/root/read/write APIs; no dedicated BCD version row | Conditional when APIs are present | Do not infer engine version from installed Chrome |
| Firefox desktop and Android | Root/read and both writers from 111 | Conditional support | Persistent original-file picker unsupported; use copy mode |
| Safari macOS and iOS/iPadOS | OPFS APIs recorded from 15.2; dedicated-worker writer before 26; async writer from 26 | Conditional with correct writer | Safari 15.2–18 cannot use an async-only OPFS writer; persistent original picker unsupported |
| Chrome / Edge / Firefox on iOS | WebKit builds follow installed WebKit; alternative-engine builds need runtime checks | Conditional on actual engine and APIs | Desktop brand/version does not establish iOS engine, quota, or picker support |

Versions come from Mozilla's browser compatibility data reviewed on the research date. Root/read support alone is insufficient: feature-detect a write path and probe actual write/read/delete. Safari's vendor documentation confirms asynchronous writable streams in Safari 26; Safari 15.2–18 requires the dedicated-worker `createSyncAccessHandle()` writer or a separately tested IndexedDB fallback. BCD records OPFS methods from 15.2, but WebKit's original article places some reading behavior at macOS 12.4/iOS 15.4. These earliest entries are **not a validated minimum for the entire app pipeline**. ([StorageManager compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/StorageManager.json), [FileSystemFileHandle compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json), [WebKit Safari 26](https://webkit.org/blog/17333/webkit-features-in-safari-26-0/), [WebKit OPFS introduction](https://webkit.org/blog/12257/the-file-system-access-api-with-origin-private-file-system/))

Firefox and Safari lacking `showOpenFilePicker()` does **not** mean they lack OPFS. It affects durable access to original external files; the existing copy-mode fallback handles that boundary. Chrome Android gained this picker in version 132, so mobile support is version dependent. On iOS, browser branding alone is insufficient: Apple permits entitled alternative engines in specified regions, but that does not identify an installed browser's engine. Feature detection and testing are required. ([Window compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/Window.json), [Chrome 132](https://developer.chrome.com/blog/new-in-chrome-132), [Apple alternative engines](https://developer.apple.com/support/alternative-browser-engines/), [Apple Japan engines](https://developer.apple.com/support/alternative-browser-engines-jp/))

**No named current major browser is categorically unable to store 128 MiB.** Even 500 MiB is possible with sufficient effective capacity, but no universal per-file guarantee was found. Negative cases are absent APIs, incompatible writers, private/embedded restrictions, denied storage, insufficient space, or resource failure. `localStorage` is unsuitable: its approximately 5 MiB string quota is far below larger song cases. An unsupported codec is a playback failure rather than a storage failure. ([Mozilla quota guidance](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria))

## Aggregate quota does not guarantee playback memory or retention

Chromium generally budgets up to roughly **60% of total disk** per origin. Firefox best-effort uses the smaller of **10% of disk or 10 GiB**, with a same-site group limit; granted persistence increases its limit. Since Safari 17, browser origins have up to approximately **60% of total disk**, while embedded nonbrowser WebKit apps have a smaller quota. These are policy maxima, not free space or reserved writable bytes. Capacitor's native filesystem adapter is separate from origin storage. ([Mozilla quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/))

Use `navigator.storage.estimate()` where available, subtract existing usage, and reserve headroom for staging, write overhead, other origin data and the retained old copy during replacement. Estimates are approximate; handle `QuotaExceededError` during writing regardless of preflight. Remove partial staging after failure/cancellation, and mark evicted audio **Not downloaded** without deleting the account track. `persist()` reduces automatic eviction when granted but cannot prevent users clearing site data or guarantee backup-grade durability. Private browsing has different budgets and usually deletes data at session end. Stable production origin matters because Vercel previews do not share one store. ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [Google OPFS guide](https://web.dev/articles/origin-private-file-system))

A Blob is an immutable encoded resource, not a promise that every byte resides in JavaScript RAM. Chromium can spill larger blobs to disk; its design describes separate memory/disk budgets and transient allocation risks. These implementation details do not establish an application-safe maximum. iOS content-process memory limits depend on hardware and current pressure. **Persistent quota is not a RAM budget.** ([Chromium Blob design](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/storage/browser/blob/README.md), [WebKit memory discussion](https://bugs.webkit.org/show_bug.cgi?id=268816#c10))

Use an HTML audio element with a completed Blob/file URL. Do not retain an additional whole-file ArrayBuffer, Base64 representation or full decoded Web Audio buffer. Fully decoding 30 minutes of 44.1 kHz stereo float32 produces **635.04 MB / 605.62 MiB** before overhead despite a 72 MB encoded track. The Web Audio standard describes AudioBuffer as intended for short memory-resident sounds and recommends media elements for longer material. This preserves full-download-before-play. ([W3C AudioBuffer](https://www.w3.org/TR/webaudio/#AudioBuffer))

## The approved song limits are 30 minutes and 128 MiB

**Approved:** enforce per-song admission on every client/source with both `duration ≤ 30 minutes` and `bytes ≤ 134,217,728` (128 MiB, approximately 134.218 MB). It covers 30-minute 320 kbps audio, ten-minute CD PCM WAV, and three-minute 24-bit/96 kHz WAV before overhead. It excludes five-minute high-resolution WAV and 30-minute CD WAV. A 60-minute 320 kbps payload is 144 MB and violates both limits. Larger/longer examples are rejection and resource-test fixtures; they are not native/cloud admission exceptions. Validate actual complete bytes including metadata and require a positive finite duration; browser memory and codec compatibility are still separate checks.

Validate accepted duration, actual file bytes and codec/container before fetching; count received bytes and cancel when the chosen cap is exceeded even if Content-Length is missing or wrong. Transport can consume chunks for progress/validation while **playback starts only after the whole encoded song completes**. Maintain one current Blob/object URL, cancel obsolete requests, and release stale resources on user track switches. No next-song preload, progressive playback, automatic persistent cache or concurrent replacement Blob is introduced. Server updates keep the current file pinned; fetch the replacement after playback finishes or is explicitly stopped/switched. ([Fetch body specification](https://fetch.spec.whatwg.org/#body-mixin), [Blob URL cleanup](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/blob))

Codec support is independent. MP3 is a practical baseline; AAC/M4A and FLAC need exact container/profile checks, while WAV can contain more than PCM. `canPlayType()` and Media Capabilities give hints; handle actual decoding failures. Automatic transcoding remains a separate product decision. Network startup is another constraint: a 72 MB download takes an ideal **57.6 seconds at 10 Mbps**, and 128 MiB takes about **107.4 seconds**, before overhead. Show progress and cancellation rather than imply instant playback. ([Mozilla codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs), [canPlayType](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/canPlayType), [Media Capabilities](https://developer.mozilla.org/en-US/docs/Web/API/Media_Capabilities_API))

Test supported desktop/Android/iOS engines with compressed/PCM boundary fixtures, 60-minute and 256/500 MiB stress fixtures, normal/private modes, low free space, denied persistence, rapid switches, backgrounding, repeated loads, interrupted transfers, wrong metadata and codec errors. No hardware measurements were performed for this research. Checklist topic 8 records the approved limits and remains open for implementation/resource and codec tests.

## Conclusion

Enforce **one per-song admission policy across clients**: at most 30 minutes and 128 MiB. Over-limit imports and replacements fail clearly; a failed replacement preserves accepted track/audio, and external originals remain untouched. OPFS eviction removes local readiness, not the account track. Real-device testing must verify memory, codecs, cancellation, quota and cloud verification within the approved limits. Any future increase requires an explicit policy change.
