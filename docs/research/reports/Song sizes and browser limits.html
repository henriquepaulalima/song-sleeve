Browser limits shape whole-song playback choices

Research date: 2026-10-07. Status: research completed; the user approved a per-song limit of 30 minutes AND 128 MiB on 2026-10-07, applied across all clients and sources. Implementation/resource tests remain pending.

Modern Chrome, Edge, Firefox, and Safari can conditionally store a single 128 MiB song; none guarantees that every device can safely fetch and play it. Ordinary 3–5-minute compressed music needs about 2.88–12 MB, while a 30-minute 320 kbps track needs 72 MB. Uncompressed and high-resolution files increase those sizes substantially. Browser disk quota, temporary Blob backing, playback memory, and codec support are separate constraints. The user has approved 30 minutes AND 128 MiB as the per-song admission limit across web, mobile, desktop, local imports, source replacements and cloud sync. Both inclusive checks must pass; this is a product rule, not a browser safety promise. The current full-download-before-play architecture remains intact. Over-limit songs are rejected rather than admitted through a native-only exception. See the current enforcement policy.

Ordinary songs need megabytes; longer WAV files need hundreds

Use 3–5 minutes for ordinary-song fixtures, 10–30 minutes for extended-song fixtures, and 60 minutes as a stress case. Chartmetric's original 2024 report places its most common chart-appearing Spotify tracks between 2:51 and 3:09 and includes a 73-minute mixtape. These observations support a popular-music baseline but do not establish a universal average for mixed personal libraries. The actual collection will be a better source for later percentile-based policy. (Chartmetric Year in Music 2024)

Every modern major browser has conditional single-file storage

The matrix describes API capability, not device measurements. OPFS stores private files for the web origin, under HTTPS, and shares the origin's quota; it does not create a visible device Songs folder. Use OPFS for explicit web copies/downloads and IndexedDB for catalog/index records. Transient cloud playback retains only the selected complete Blob and object URL; it does not automatically create an offline copy. (Google OPFS guide)

Firefox and Safari lacking showOpenFilePicker() does not mean they lack OPFS. It affects durable access to original external files; the existing copy-mode fallback handles that boundary. Chrome Android gained this picker in version 132, so mobile support is version dependent. On iOS, browser branding alone is insufficient: Apple permits entitled alternative engines in specified regions, but that does not identify an installed browser's engine. Feature detection and testing are required. (Window compatibility, Chrome 132, Apple alternative engines, Apple Japan engines)

No named current major browser is categorically unable to store 128 MiB. Even 500 MiB is possible with sufficient effective capacity, but no universal per-file guarantee was found. Negative cases are absent APIs, incompatible writers, private/embedded restrictions, denied storage, insufficient space, or resource failure. localStorage is unsuitable: its approximately 5 MiB string quota is far below larger song cases. An unsupported codec is a playback failure rather than a storage failure. (Mozilla quota guidance)

Aggregate quota does not guarantee playback memory or retention

Chromium generally budgets up to roughly 60% of total disk per origin. Firefox best-effort uses the smaller of 10% of disk or 10 GiB, with a same-site group limit; granted persistence increases its limit. Since Safari 17, browser origins have up to approximately 60% of total disk, while embedded nonbrowser WebKit apps have a smaller quota. These are policy maxima, not free space or reserved writable bytes. Capacitor's native filesystem adapter is separate from origin storage. (Mozilla quotas, WebKit storage policy)

Use navigator.storage.estimate() where available, subtract existing usage, and reserve headroom for staging, write overhead, other origin data and the retained old copy during replacement. Estimates are approximate; handle QuotaExceededError during writing regardless of preflight. Remove partial staging after failure/cancellation, and mark evicted audio Not downloaded without deleting the account track. persist() reduces automatic eviction when granted but cannot prevent users clearing site data or guarantee backup-grade durability. Private browsing has different budgets and usually deletes data at session end. Stable production origin matters because Vercel previews do not share one store. (WebKit storage policy, Google OPFS guide)

A Blob is an immutable encoded resource, not a promise that every byte resides in JavaScript RAM. Chromium can spill larger blobs to disk; its design describes separate memory/disk budgets and transient allocation risks. These implementation details do not establish an application-safe maximum. iOS content-process memory limits depend on hardware and current pressure. Persistent quota is not a RAM budget. (Chromium Blob design, WebKit memory discussion)

Use an HTML audio element with a completed Blob/file URL. Do not retain an additional whole-file ArrayBuffer, Base64 representation or full decoded Web Audio buffer. Fully decoding 30 minutes of 44.1 kHz stereo float32 produces 635.04 MB / 605.62 MiB before overhead despite a 72 MB encoded track. The Web Audio standard describes AudioBuffer as intended for short memory-resident sounds and recommends media elements for longer material. This preserves full-download-before-play. (W3C AudioBuffer)

The approved song limits are 30 minutes and 128 MiB

Approved: enforce per-song admission on every client/source with both duration ≤ 30 minutes and bytes ≤ 134,217,728 (128 MiB, approximately 134.218 MB). It covers 30-minute 320 kbps audio, ten-minute CD PCM WAV, and three-minute 24-bit/96 kHz WAV before overhead. It excludes five-minute high-resolution WAV and 30-minute CD WAV. A 60-minute 320 kbps payload is 144 MB and violates both limits. Larger/longer examples are rejection and resource-test fixtures; they are not native/cloud admission exceptions. Validate actual complete bytes including metadata and require a positive finite duration; browser memory and codec compatibility are still separate checks.

Validate accepted duration, actual file bytes and codec/container before fetching; count received bytes and cancel when the chosen cap is exceeded even if Content-Length is missing or wrong. Transport can consume chunks for progress/validation while playback starts only after the whole encoded song completes. Maintain one current Blob/object URL, cancel obsolete requests, and release stale resources on user track switches. No next-song preload, progressive playback, automatic persistent cache or concurrent replacement Blob is introduced. Server updates keep the current file pinned; fetch the replacement after playback finishes or is explicitly stopped/switched. (Fetch body specification, Blob URL cleanup)

Codec support is independent. MP3 is a practical baseline; AAC/M4A and FLAC need exact container/profile checks, while WAV can contain more than PCM. canPlayType() and Media Capabilities give hints; handle actual decoding failures. Automatic transcoding remains a separate product decision. Network startup is another constraint: a 72 MB download takes an ideal 57.6 seconds at 10 Mbps, and 128 MiB takes about 107.4 seconds, before overhead. Show progress and cancellation rather than imply instant playback. (Mozilla codec guide, canPlayType, Media Capabilities)

Test supported desktop/Android/iOS engines with compressed/PCM boundary fixtures, 60-minute and 256/500 MiB stress fixtures, normal/private modes, low free space, denied persistence, rapid switches, backgrounding, repeated loads, interrupted transfers, wrong metadata and codec errors. No hardware measurements were performed for this research. Checklist topic 8 records the approved limits and remains open for implementation/resource and codec tests.

Conclusion

Enforce one per-song admission policy across clients: at most 30 minutes and 128 MiB. Over-limit imports and replacements fail clearly; a failed replacement preserves accepted track/audio, and external originals remain untouched. OPFS eviction removes local readiness, not the account track. Real-device testing must verify memory, codecs, cancellation, quota and cloud verification within the approved limits. Any future increase requires an explicit policy change.
