Music app stack review

Review date: 2026-10-07. Status: recommendations for review, not approved stack changes. The current React/TypeScript/Vite, Go/Gin, PostgreSQL and Railway bucket choices can implement Song Sleeve's accepted rules. The largest missing capabilities are native file permissions, native playback and background reconciliation, a selected desktop shell, and explicit durable transfer/deletion protocols. Replacing the database or HTTP framework would not supply those capabilities. Keep the core, make its supporting libraries concrete, and test installed-client adapters before investing in all screens. This review proposes Wails as the first desktop candidate and retains Capacitor conditionally; Expo is an alternative if mobile feasibility tests fail. Deployment remains Vercel for web and Railway for API, workers, PostgreSQL and optional cloud audio. The evidence establishes documented tools and limitations; no application, hardware benchmark or deployment was built.

The existing core fits; supporting capabilities remain unselected

The app is a relational account catalog with separate file delivery. A stable track document owns metadata, its optional artist and one current content reference; every newly confirmed source submission creates fresh content, including an identical file. Artists are explicit assignments, playlists manually contain tracks, and groups manually contain playlists. Cloud audio is opt-in. Installed clients play local Songs copies or unsynced linked originals; web fetches one complete selected song. All imports and account edits require server acceptance, so a database designed around offline document writes offers limited benefit. These product decisions are the basis for the assessments below, rather than optional assumptions. (Current implementation plan)

The proposal adds capability boundaries rather than more network services. A shared TypeScript domain layer can handle accepted catalog documents, queue order and view models while platform adapters own file access, player resources, credentials and local persistence. Keep one modular Go API and independently scalable worker process. No evidence justifies separate artist/playlist microservices, Redis, Kafka or a distributed database at the start. The component matrix is an architectural judgment based on documented APIs below, not a claim that any selected package supplies the entire app.

React reuse succeeds only when installed work has native owners

React's guidance explicitly presents Vite as a SPA tool while leaving routing and data fetching to additional choices. React Router can provide client navigation without a second backend; TanStack Query can manage accepted API results; dnd-kit provides accessible pointer/touch/keyboard ordering. These are proposed additions. Mount player and reconciliation controllers above route pages, and keep transport work out of list components. Large libraries also need pagination and a clear reorder contract for unloaded items, rather than loading every row to make dragging convenient. (React guidance, React Router, TanStack mutations, dnd-kit)

The accepted online-only policy conflicts with automatic deferred mutations. TanStack's network handling can pause work until reconnection. For account mutations, reject known disconnection, use an actual authenticated API attempt, disable retry and mutation persistence/replay, and apply authoritative values only on acceptance. A proposed networkMode: 'always' with retry: false avoids treating disconnected actions as paused writes; a failed response still requires request-status lookup because the server could already have committed. Cached reads and local play/seek/shuffle remain separate. (TanStack network modes)

Browser local storage differs from installed storage. Ordinary file inputs do not grant persistent authority to external paths. showOpenFilePicker() has limited cross-browser availability; OPFS provides an origin-private controlled copy rather than a visible OS Songs folder. Propose Dexie for IndexedDB catalog records and capability-driven OPFS adapters for explicit copies/offline downloads. Offer copy/reselection when original linking cannot persist. Preserve 30 minutes AND 128 MiB as admission rules, not a universal RAM guarantee: web must finish the selected encoded-song fetch, own one Blob/object URL, cancel obsolete loads and release it before another song resource. No library should silently prefetch audio or convert the whole song to Base64/decoded memory. (File input, Persistent picker, OPFS, Dexie, Browser research)

Capacitor remains a reasonable mobile choice, but filesystem access alone is insufficient. Android links require Storage Access Framework URI grants and persistence; iOS requires security-scoped URLs/bookmarks and coordinated access. Permissions can be revoked and originals can move. Official Filesystem native binary reads use strings/Base64, so use native file paths/transfers/checksum operations instead of loading whole audio into React. Persistent app storage should hold account-scoped managed songs; backup policy and external-original protection need explicit handling. (Android file access, Apple directory access, Capacitor Filesystem)

A mobile music player needs a native engine that survives UI suspension: Android Media3 MediaSessionService, and iOS playback audio-session/background capability plus system media controls. Capawesome's paid Audio Player documents local URI playback, media controls and native playlist advancement; its paid File Manager documents retained directory grants and checksums, with File Picker providing directory/bookmark selection. These are evaluation candidates, with licensing/update costs and individual-file persistent access still to verify. An HTML audio element plus WebView callbacks is not evidence of reliable minimized playback, repeat/reset or deferred file installation. (Media3, Apple audio session, Capawesome Audio Player, File Manager, File Picker)

Capacitor's official Push Notifications plugin does not handle iOS silent pushes; killed Android handling requires a native messaging service. Background Runner is bounded, with approximately 30 seconds on iOS and inexact periodic scheduling. Implement native FCM/WorkManager and APNs/background URLSession adapters that can authenticate, persist catch-up and coordinate files without React executing. Expo offers a documented native audio/lock-screen path if Capacitor testing fails, but replacing mobile UI components adds work and Expo still follows OS background scheduling. No framework promises immediate updates on suspended or force-stopped phones. (Capacitor push limits, Background Runner, WorkManager, Apple downloads, Expo Audio, Expo background tasks)

Desktop remains a selection gap. Evaluate Wails first: it combines React/TypeScript with local Go services and system rendering engines, matching the user's preferred languages. Those local services are separate from Gin on Railway. Tauri provides scoped filesystem/SQLite plugins and a small system-WebView approach, adding Rust; Electron provides a Node main process and consistent Chromium environment with a larger bundled runtime. None automatically supplies the finished player, media controls or durable original grants. Host minimized sync outside window React lifetimes and test codecs, sleep/resume, signing, updates and account cleanup. (Wails, Wails window lifetime, Tauri, Tauri SQLite, Electron process model, Electron security)

PostgreSQL and Gin fit; transactions define correctness

Keep PostgreSQL. Composite foreign keys and uniqueness can enforce same-user artists, playlist-song and group-playlist references and one current content pointer. The “track document” is an API representation, not a requirement for MongoDB. MongoDB supports transactions but does not eliminate relationship validation; SQLite has a single-writer constraint and is better suited to device replicas here; Turso's offline-write synchronization is less relevant because edits require server acceptance. No comparative workload benchmark justifies switching engines. (PostgreSQL constraints, MongoDB transactions, SQLite uses, Turso)

Gin provides routing, middleware, binding and SSE primitives. Propose pgx/pgxpool for PostgreSQL access, sqlc for typed SQL queries, Goose for controlled migrations and OpenAPI generation with oapi-codegen for contracts. Chi is a reasonable standard-handler alternative; changing routers would not remove source revisions, account gates or transactions. An ORM can implement these operations, but explicit SQL keeps ownership predicates and replacement/receipt/outbox commits visible. Device SQLite remains an accepted replica and work index; selecting its plugin must prove native-background-worker access and a single file/index coordinator. (Gin, Chi, pgx, sqlc transactions, Goose, OpenAPI generator, Native SQLite API)

Propose River for PostgreSQL-backed durable Go jobs: enqueue mail, verification and cleanup in the same transaction as the corresponding accepted change. Keep replayable domain events separate from queue internals. River uniqueness and retries are not the per-user/track serialization rule: uniqueness includes job kind, and execution is at least once. Use a database operation coordinator keyed by stable (user_id, track_id) across upload, replacement, restore download and unsync. Its owner, lease and fencing generation validate completion; grants must remain safely retired before another operation starts. Same-song downloads across devices wait in order under the accepted rule. Never hold a database transaction throughout a transfer or playback session. (River enqueue, River uniqueness, PostgreSQL locking)

Accepted metadata, receipts and outbox events commit together. A PostgreSQL LISTEN/NOTIFY connection per API replica can wake a fanout dispatcher; device SSE streams should not each reserve a database connection. Notifications are hints while persisted per-user cursors supply replay and snapshots after expired history. Redis Pub/Sub could later improve fanout, but disconnected subscribers lose messages and it cannot replace history. Firebase Admin's Go sender can support Android and Apple delivery through APNs; direct APNs is an alternative adapter. (PostgreSQL NOTIFY, Redis semantics, Firebase Admin Go, Apple delivery)

Railway storage fits only with verified publication and recovery

Railway Buckets provide private S3-compatible object storage, presigned transfers and COPY. Official documentation confirms encryption at rest, no automatic bucket backups and public-network-only access. Configurable S3 encryption settings, versioning, locks and lifecycle rules remain unsupported; infrastructure encryption does not establish account-specific cryptographic erasure. Keep AWS SDK for Go v2 behind ObjectStore and verify the exact optional headers/conditions rather than treating “S3-compatible” as universal AWS parity. (Railway buckets, Official FAQ source, Go S3 endpoints)

The resource tradeoff is favorable for direct client transfers: documented bucket storage is $0.015/GB-month, with free bucket operations/egress, but Railway worker uploads incur service egress. Opt-in audio alone consumes bucket capacity. A trusted verification worker still needs bounded temporary disk, checksum computation and ffprobe to enforce positive finite duration and actual total bytes before readiness. Unsynced device-only bytes cannot be independently probed by Gin. Enforce 1,800 seconds and 134,217,728 bytes without changing accepted content on rejection, and measure worker concurrency/temp disk instead of loading complete songs into the Go heap. (Bucket billing, ffprobe)

Presigned PUTs must target staging, never final accepted content. AWS documents reusable URLs and overwrite-at-key behavior; this hazard needs Railway compatibility tests. Even a unique staging key can change between probing and unconditional COPY while its grant remains live. The proposed safe baseline downloads/counts/hashes/probes staging once, uploads those exact verified temporary bytes to a fresh server-only final key, verifies final, then atomically publishes the track/content reference. Conditional copy is a later optimization requiring provider proof. Every deliberate new source still creates fresh content; retries retain their existing operation. Publication can add worker egress, but prevents an apparently immutable generation from changing after verification. (Presigned semantics, Railway serving patterns)

Google Drive remains an import origin, never canonical storage or an installed playback URL. Preserve Drive-to-device download into managed Songs and upload to Railway only after explicit cloud opt-in. The existing scope guidance limits drive.file to files explicitly opened/shared with the app, so design Google Picker authorization on web separately from native OAuth/document-provider selection. Folder traversal, grant persistence, cancellation, byte limits and recovery after interrupted downloads need an integration spike; a filesystem plugin does not implement Drive authorization. Provider quota/pricing and OAuth verification should be rechecked when selecting the exact flow. (Drive scope guidance, Current Drive flow)

Removal must drain/expire capabilities, abort multipart work and clean late-written staging. Missing lifecycle rules make orphan/multipart cleanup application responsibilities. Independent backups/inventory matter because the bucket is the recovery origin for installed mirrors. Railway documents a whole-bucket recovery window, which does not prove per-object physical-erasure timing. Provider retention and conditional/checksum guarantees remain questions for the storage spike. Keep another provider behind the adapter as an escape path if these guarantees fail; reopening provider comparisons does not authorize moving production storage now. (Railway buckets)

Railway PostgreSQL templates are unmanaged: configure monitoring, backups, security and restore procedures. Optional PgBouncer, PITR and HA are additional deployment choices, not defaults. Bounded driver pools are sufficient initially; session-scoped LISTEN needs a dedicated/unpooled connection when transaction pooling is introduced. Railway's optional PITR retains approximately four weeks of full backups; scheduled volume snapshots retain daily/weekly/monthly copies for 6/27/89 days. Shared historical snapshots need a deletion-retention policy and an independently retained deletion ledger reapplied before restored traffic. An external managed PostgreSQL provider becomes justified by operational/RPO/RTO requirements, not a different catalog model. (Railway databases, PgBouncer, PITR, Snapshots)

Deployment and lifecycle protocols need targeted proof first

Vercel fits the static Vite SPA; persistent API/worker/event services belong on Railway. Vercel Functions' 4.5 MB body limit is incompatible with proxying admitted audio. Direct browser/native bucket transfers preserve the architecture. Railway public HTTP requests close after 15 minutes despite traffic, or five minutes without data; SSE needs heartbeats plus authenticated reconnect, jitter/backoff and cursor replay. WebSockets avoid those particular edge limits if reconnect overhead later warrants a change, but not session revocation or replay requirements. (Vite deployment, Vercel limits, Railway networking limits)

Use HTTPS app.example.com on Vercel and api.example.com on Railway for same-site web cookies; they remain cross-origin and require exact credentialed CORS plus CSRF. Default provider domains are cross-site, so do not depend on third-party cookies. Keep native tokens in secure platform storage accessible under the chosen background policy. Go's random/Argon2id primitives and optional session-store adapters support the approved 30-day absolute opaque sessions, verification/reset and revocation, but Gin is not a full identity product. Recovery email provider selection, protected reset page and deletion-only credentials remain separate work. (OWASP CSRF, Go Argon2id, OWASP sessions, OWASP recovery)

Transactional email is a missing provider decision. Verification and reset tokens need hashed, expiring single-use records, encrypted transient link material, and transactional job enqueue; the provider adapter needs delivery retries and idempotency until expiry. Do not assume River encrypts sensitive job arguments. Instrument accepted-request latency, database pools/query plans, queue age/retries, per-track wait time, SSE reconnects, verified media bytes/temp disk, service egress and device-applied status. Scale only the measured bottleneck; monitor stalled deletion and failed cleanup separately from ordinary jobs. (River transactional jobs, OWASP recovery)

Non-cancellable deletion requires a durable ledger, not unlimited queue optimism. River defaults to a retry cutoff, so an incomplete deletion must remain pending and be recovered/re-enqueued with alerts; queue failure cannot declare deletion complete. Revoke sessions first, drain work, erase owned objects/rows, delete the user last, and keep cleanup receipts independent. Installed and browser clients cancel callbacks, stop deletion-affected playback immediately, purge account namespaces and acknowledge verified removal. Ordinary replacement/unsync still preserves active playback until its safe boundary. Offline devices and shared backups retain the documented execution/retention limits. (River retries, Accepted deletion flow)

Conclusion

The decision to make next is whether installed adapters can meet the product's file and lifecycle contracts at an acceptable maintenance cost. If those proofs succeed, adding more databases or replacing Gin would increase migration work without resolving the remaining risks. If a native capability fails, replace that adapter or mobile shell while preserving the TS domain layer, Go services and account protocol.

The concrete proposed baseline is React/Vite plus routing/query/order adapters, Capacitor with native-owned player/sync/storage services, a Wails desktop feasibility trial, Gin with pgx/sqlc/Goose, PostgreSQL with River workers, and private Railway objects published from verified bytes. Read the supporting client notes, Go-service notes and database/storage/deployment notes. The moved storage/database comparison is a historical 2026-10-03 snapshot; its streaming/deduplication and provider recommendations are superseded by the current plan and this review. Checklist items 5–9 remain open for protocol details and implementation validation.
